# Runes 1.x: the stable API

This is what `@chrisdudek/runes` promises under semantic versioning from 1.0.0 on. A name listed here keeps its meaning and its signature for every 1.x release: a minor release may add names, options and fields, a patch release fixes behaviour to match what the README says, and anything that breaks a listed name waits for 2.0.0. A test (`test/exports.test.mjs`) holds this page and the package's exports together both ways, so a name exported without being listed here, or listed without being exported, fails the build.

## What the promise covers

- **The names below**, from the six subpaths, with the behaviour the README documents for them. Types are part of it: a type listed here keeps its fields (a minor release may add optional ones).
- **The module files a vendoring consumer imports** without going through an index: `dist/version.mjs`, `dist/<subpath>/index.mjs` for each subpath, and in the test kit `dist/testkit/parity.mjs`, `dist/testkit/measure.mjs`, `dist/testkit/client.mjs` and `dist/testkit/runtime/index.mjs`, each with the names it exports today. A vendored copy takes whole directories or these files, so these paths are the vendoring surface; every other file under `dist/` may move in any release, and `dist/fs/` is not a subpath (see below).
- **The documents and formats**: the `<tool>-error/1` error document; the grammar manifest (`grammars/manifest.json`, its schema id); the vendoring pin (`runes.pin.json`), the commands, options and exit codes of `tools/vendor.mjs`, and the skill fragment names and markers.
- **The MCP wire shape** the adapter generates: tool names, one field per argument and flag with its type, which fields are required, what the annotations mean, one JSON block with notes in `_meta`, -32602 for input that does not fit, cancellation and time limits.

## What it does not cover

- Every export of an internal module. The per-language extractors by name (all but `csharpExtractor`; `extractorForLanguage` is the promised way to one), the in-process MCP executor, the git test environment (`gitEnv`, `makeTempRepo`), the per-language resolution helpers, the table's helper functions, the command-line parser, the error document and the one-block `--json` rule, the usage-text reader, the guard's scanner and the git environment's constants stay in their modules for Runes' own code and tests; they may change in any release.
- The file-system code under `dist/fs/` (the cross-process lock, atomic writes, the repository root). It ships and is tested, but no subpath exports it and no family tool uses it yet; it may change in any release until a 1.x minor exports it for a tool that adopts it.
- Wording: error messages, tool and field descriptions, report lines. Codes (`code` in the error document, `ELOCKED`, `ELOCKBREAK`, `usage`, and `config-unreadable` and `package-entry-missing` of a relation diagnostic) are stable; sentences are not.
- The exact edges an extractor finds. An extractor fix changes what it reports for some source, in a minor or a patch release; the extractor's `rev` changes with it, so a consumer's cache keyed by `rev` drops what it computed before. The relation catalogue (`reference/relations/`) is the specification that fixes move towards.

The Consumers column names the family tools that import each name on their `release/6.1.0` branches (sources and tests; a vendored copy counts), found by reading their imports. 1.0.0 promises only what a family tool imported when it was written, and a 1.x minor adds a name, additively, when a tool adopts it. Two value exports, `toolName` and `startMcpClient`, were imported only by Horde, which has since left the family; they stay exported and promised, and carry "—" until a tool imports them.

A type marked "—" is imported by no tool and is kept because a kept export's signature reaches it: it is a parameter, a return value or a field of one, so without its name a TypeScript consumer could not write down what it passes to or gets back from a promised function (`TreeSitterRuntime` is what `ParserHostOptions.runtime` takes, `PrepareResult` what `ServerOptions.prepare` returns). Its fields are promised through that signature whether or not the name is exported, so exporting the name adds no promise. A type reached only through a removed name went with it (`InProcessExecutor`, `CallContext`, `GitEnvOptions`, `TempRepo`).

`version` (the package version, the same value on each subpath that has it) is exported by `relations`, `ast` and `grammars`, where Yggdrasil reads it: it keys its relation cache on the `relations` one and pins all three against its dependency. `cli`, `mcp` and `testkit` export none, since no tool reads one there; a vendoring consumer that wants the version reads `RUNES_VERSION` from `dist/version.mjs`.

**The file view (added in 1.1.0).** Resolution reads the repository: whether a candidate file exists, which files a directory holds, the text of a `tsconfig.json`, a `package.json`, a `Cargo.toml`, a `go.mod`, a `composer.json`, a `compile_commands.json` or a `.csproj`, and which Python manifests (`pyproject.toml`, `setup.cfg`, `setup.py`) a directory holds, by name only: their text is not read. By default it reads the disk under the project root, as 1.0.x did, and a consumer that passes nothing sees no change. A consumer that resolves the contents of one commit passes `makeResolvePathToFile(projectRoot, ownerOf, isExcluded, { files })` (and `buildCsharpProjectScopes(projectRoot, facts, { files })`) with a `FileView`, so an untracked or ignored file on disk (build output, a generated config, an installed package) cannot decide where an import lands, and the same commit gives the same edges on every machine. `FileView` has five methods (`exists`, `isFile`, `isDirectory`, `list`, `read`) over POSIX paths relative to the project root, `''` being the root. `listedFileView(paths, read)` builds one from a list of file paths (the directories are the ones the list implies) and a reader for their text: anything not listed does not exist, so a symbolic link is absent unless it is listed, there is no `node_modules` unless it is listed, and names are compared exactly. Runes spawns no git and makes no decision about what "the commit" is: the consumer supplies the list and the reader. `isExcluded` keeps its meaning on top of the view. Every read of every language's resolver goes through the view; with a view given, the disk is not touched, and an exception the view's `read` throws reaches the caller of the resolver. The consumers named in the table adopt it in the 6.2.0 pickups: Yggdrasil (package Y5) passes the files git would commit, Grain (package G9) the files of `HEAD`; both land after this release's Runes commit is final, so until then neither tool's published code imports `makeResolvePathToFile`'s `{ files }`, `FileView` or `listedFileView`.

**C# reachability (added in 1.1.0).** C# binds a name only to a declaration of its own compilation or of an assembly the compilation references, and the extractors read one file at a time, so every in-repository declaration of a name was a candidate, including an extension method or a type of a project the calling project cannot see: a false relation that no declared relation could answer. `buildCsharpReachability(projectRoot, csFiles, { files })` reads the reference graph of the repository's projects and returns a `Reachability`, a function `(fromFile, targetFile)` answering `'same'` (one project), `'reachable'` (the target's project is in the caller's closure), `'unreachable'` or `'unknown'` (the graph can say nothing: a file with no project facts, or a caller that reaches an open project); a consumer passes it as `ResolverDeps.reach` to `makeResolver`. With `reach` given, a symbol hint of a C# file loses every definer in a project its project cannot reach before the owners are counted, and when a definer lies in the file's own project only that project's definers stay (the compiler prefers a type of its own compilation to a referenced one of the same name; an extension method has no such preference, the compiler chooses among them by overload resolution); `unknown` filters nothing; the global `Program`, declared (`public partial class Program { }`) or synthesized from top-level statements, is one name to the compiler, so when the graph says something about every definer of it the two kinds are chosen among together (the one in reach, or silence when two referenced projects each have one), and when it can say nothing about one of them the order of a pass without a graph stays: the declared class first; `resolve`, `classify` and `resolveFile` all apply it, and the path axis and every other language are untouched. A reference graph is read from the project files (`*.csproj`, and `*.fsproj` and `*.vbproj` a chain passes through) and every `Directory.Build.props` and `Directory.Build.targets` above them: `ProjectReference` (a path, read against the file that holds it and, in an imported file, against the project too; a wildcard; `$(MSBuildThisFileDirectory)` and `$(MSBuildProjectDirectory)`), `Reference` by name, by the file name of an `Include` that is the assembly's path, or by `HintPath` file name, and `PackageReference`, the last two against the assembly names (set in a project file or in a `Directory.Build.*` file) and package ids of the repository's own projects; every directory and file name of a path is matched in any case; references are transitive, conditions are read and never evaluated, and an imported file the view holds is read too. A file of a project's directory that a `<Compile Remove>` of the project takes out (and no `<Compile Include>` of it names again) is in no compilation of that project: as a target it is `unreachable` from every file, its own project's included, and as a caller it is `unknown`; a removal under a condition (its value may hold a raw `>`) or inside a target is not read, because it may not apply, and a project with a `<Compile Include>` whose path needs a property this reader does not know keeps every file, because that include may put any of them back. Everything unknown fails open: a project with a reference path that needs another property or names no file of the repository, a `Compile` item whose path needs another property or leaves the repository, an unresolvable import, an unconditional import of a file the view does not hold or a shared-project import is open and reaches everything, and so is every project that reaches an open one; a file that another project links through a `Compile` item outside that project's directory is code of that project too, and the link adds that file to it and nothing else: as a caller the file sees what that project references, as a target it is seen by that project (`same`) and by every project that reaches it, and a linked file under no project file belongs to the projects that link it alone; a file under no project file, or not among `csFiles`, is reachable from and to everything. The worst case is therefore the answer without `reach`, and a consumer that passes nothing sees no change. A `Reachability` built here also answers `internalsVisible(fromFile, targetFile)`, an optional member of the type: true when the two files share a compilation, or when a compilation of the target that the caller reaches names the caller's assembly (its project file's name, its `<AssemblyName>` or its `<PackageId>`) as a friend, through an `<InternalsVisibleTo Include>` item (`$(MSBuildProjectName)` and `$(AssemblyName)` read as the defining project's names), an `<AssemblyAttribute Include="…InternalsVisibleTo">` item, or an `[assembly: InternalsVisibleTo("…")]` attribute in a C# file the project compiles (read only when a caller first asks about that project); a grant it cannot name (an unknown property, a constant) names every project, and a pair the graph knows nothing about is visible. The C# extractor declares a type or an extension method that only its own assembly sees (`internal`, `private`, a top-level type with no access modifier, a type nested in one of those, an extension method that is not public or whose class is not; a `partial` part without an access modifier is never counted) a second time under the marker key `internal:<key>`, which no C# name can produce, so it never binds a reference. With `reach` given and answering `internalsVisible`, a definer in a reachable project of another compilation whose declarations of the name all carry the marker is dropped for a caller that is not a friend; a `Reachability` without the member drops none. `csFiles` is the repository-relative C# files the pass holds, `files` the same `FileView` the other readers take (without it the disk under `projectRoot` is read). The consumers named in the table adopt it in the 6.2.0 pickups (Yggdrasil package Y5, Grain package G9), so until then neither tool's published code imports it.

**Unreadable configuration (added in 1.1.0).** `ResolvePathOptions.onDiagnostic` receives a `RelationDiagnostic` (`code`, `file`, optional `line` and `column`, `message`) when resolution consults a configuration file it cannot read, so an absence of edges under it is no longer silent. It is called synchronously, at most once per `(code, file)` for one resolver, and only for a file resolution actually consulted. Of the two codes today, `package-entry-missing` is described below and `config-unreadable` is for a `tsconfig*.json`, `jsconfig*.json`, `package.json`, `composer.json` or `compile_commands.json` that does not parse and for a `pnpm-workspace.yaml` whose `packages:` list cannot be read; `file` is the repository-relative path, and `line` and `column` (1-based) are where the failure lies in the file as written, comments and trailing commas included, counted from after a byte order mark as an editor shows it. A position is given when the JSON parser names one, when the input ends too soon (the end of the file), or when the parser names none but the offending token is unambiguous (a single-quoted string, an unquoted value, `undefined`, or a whitespace character JSON does not allow such as a no-break space), and then it is that token. Where the parser quotes a character that is not the one Runes finds (a structural character where a value belongs: `{"a": }`, `[1,,2]`, a trailing comma in strict JSON, `{"a": : 1}`), `line` and `column` are absent and the message names none: the file is reported without a position, never with a guessed one. Lines end at LF, CR or CRLF. `code` is a `string` and stays stable; `message`, `line` and `column` are best effort and not part of the promise. A tsconfig, jsconfig, package.json, composer.json or compile_commands.json with a byte order mark reads fine and never reports. The consumers named in the table adopt the callback in the 6.2.0 pickups: Yggdrasil (package Y5) turns each diagnostic into a warning, Grain (package G9) discloses them in its export and propose report; neither imports it before then. Resolution is unchanged: an unreadable file still governs nothing; the callback only makes that visible. The Cargo, `go.mod` and project-file readers take their lines as they find them and never fail to parse, so they report nothing.

**Package entries under build output (added in 1.1.0).** A package whose `exports`, `types`, `typings`, `module` or `main` names a file that is not in the repository (build output a clean checkout does not hold) is read through the package's own TypeScript project: every `tsconfig.json` and `tsconfig.*.json` directly in the package directory whose `outDir` holds the entry (for a declaration, its `declarationDir` when set) maps it back to the source under `rootDir`, so `dist/a/b.js` and `dist/a/b.d.ts` name `src/a/b.ts` or `src/a/b.tsx`, `.mjs` and `.d.mts` a `.mts` file, `.cjs` and `.d.cts` a `.cts` file, and a JavaScript source counts under `allowJs`. A dual package that a bundler builds (tsup, unbuild) names its two builds by format, `dist/index.mjs` with `dist/index.d.mts` and `dist/index.cjs` with `dist/index.d.cts`, all from `src/index.ts`: where no `.mts` or `.cts` source of that name is there, such an entry names the `.ts` or `.tsx` source. Without `rootDir` the root is the one the compiler computes, the common directory of the project's sources or the tsconfig's directory, and both are tried. A reading counts when it names a file the project holds, and all readings that count must name one file; otherwise nothing binds. A tsconfig that sets `noEmit` or holds no source writes no output and is not asked. An entry that is in the repository is the target as before, so the answer is the same before and after a build only when the consumer passes ignored output as excluded or resolves through a `FileView` of the commit. When an entry names no file and gives no source (no tsconfig maps it, or the tsconfigs map it to different sources, and the message says which), and nothing else binds the import, `onDiagnostic` receives `package-entry-missing` once per package: `file` is the package's `package.json`, the message names the entry, and there is no `line` or `column`. It is sent for the first import that binds nothing for this reason, and the message names the entry that import reached; an import of the same package that reaches another entry (another `exports` subpath or condition) may still resolve. A consumer may show it as a warning that an import reaching that entry is not resolved.

**Same-package references (added in 1.1.0).** The Java and Kotlin extractors now give a candidate group for a simple type name written without an import, because a type of the package is in scope in every file of the package (in Kotlin after an explicit import or alias, and before a star import and the default imports; a capitalised callee such as `Owner(...)` counts as well as a receiver, and a lowercase name is never read). The group holds, in order, the member types a supertype of an enclosing declaration may inherit (`<package>.<Super>+<Name>`) and then `<package>.<Name>`, both symbol hints resolved through the shared JVM namespace, so a Kotlin class of the package counts too. `TargetHint` (the `symbol` form) gains the optional field `samePackage`: `true` marks a key that names a type of the referencing file's own package, and `makeResolver` then lets the file see only the definers its source set can see. For the Maven and Gradle layout `<module>/src/<set>/java|kotlin/…`, code of a main-like set (`main`, a variant such as `debug`) never sees a class of a test-like set (`test`, `testFixtures`, `integrationTest`, `it`, `jmh`, `androidTest`, a multiplatform `…Test`), whichever module holds it; a test-like set sees main-like sets, its own set and the `testFixtures` of any module, and not another test-like set of its own module. A path outside that layout counts as visible. A hint without the field resolves as before, and a consumer that passes hints through `makeResolver` needs no change. The same-package group is not emitted where the simple name means something else (a type parameter in scope, a type the file declares, an import of that name or an alias for it, for a receiver a variable of that name), and a file of the unnamed or root package gives none; neither does a Kotlin file whose declarations could not all be read. Known limits, each with a catalogue case or a note: a member type inherited from a supertype outside the repository (or from a supertype's own supertype) is not known; a capitalised field (Java) or property or function (Kotlin) of that name that a static on-demand import or a supertype brings obscures a receiver and is not seen. What a consumer's graph now shows: a test that uses a class of its own package depends on the component that holds that class, so a graph that keeps tests and production code in separate components needs that relation declared.

**C# using directives by namespace block (added in 1.1.0).** A plain C# `using N;` inside a namespace block now reaches only the references of that block and of the blocks nested in it. It is read at its block's namespace, before the next namespace outward. The namespace it names is read where it stands: `using Core;` inside `namespace A` names `A.Core` when the repository declares that namespace. `TargetHint` (the `symbol` form) and `SymbolSetMember` gain the optional field `shadow`, a list of dotted names. When the repository declares one of them, as a type or as a namespace some declared key lies in, `makeResolver` treats the reading as absent and goes on to the next candidate. A hint without the field resolves as before. `SymbolTable` gains `hasNamespace(language, name)`, true when some declared key of that language lies inside the dotted namespace `name`. `CsharpExtract` changes shape: `scope.prefixDecls` lists each plain using with its block, the `target` and `ext` descriptors carry `at`, and each `outer` entry of a `target` descriptor carries `statics`. A consumer that stores the extract stores these fields too; an extract stored by an earlier build is stale, and the C# extractor's `rev` says so. `scope.aliasDecls` lists each using alias with its block in the same way. A using written after `global::` (`using global::Core;`) names the global namespace `Core` only, and the extract keeps that form: an entry of `scope.prefixDecls` holds the namespace without the qualifier and `rooted: true`, and the `prefixes` of an `outer` entry keep the namespace as written, `global::Core`. `scope.prefixes` still lists the namespace of every plain using without its block; the extractor no longer reads it, and it stays because a consumer that stores the extract reads it. The `target` descriptor has no `nearest` field: an earlier build of the 1.1.0 branch had one, and an extract stored by that build is stale by its `rev`.

**C# nested types of the enclosing types (added in 1.1.0).** C# reads the nested types of each type around a simple name, innermost type first and from every part of a partial type, before any namespace, alias or using. Inside `CreateOrder.Handler`, `Command` names `CreateOrder.Command`, not a `Command` of an enclosing namespace or an import. The C# candidate group of a simple or dotted name written inside a type now starts with one reading per enclosing type, `<namespace>.<Outer>+<Name>`, innermost first; a dotted `X.Y` reads `<Outer>+X.Y`, which the resolver binds as the nested `<Outer>+X+Y`. The nested readings apply inside a type's body only: its attributes, its base list and its constraint clauses lie outside it (C# spec §7.7.1), so `class Handler : Command { class Command { } }` derives from the `Command` around it. The `plain`, `attr` and `receiver` descriptors of `CsharpExtract` gain the optional field `types`, the declaration keys of the types whose bodies hold the reference, innermost first (`['App.Web.CreateOrder+Handler', 'App.Web.CreateOrder']`); it is absent outside every type body and on a `global::` reference. An extract stored by an earlier build lacks the field and is stale by the C# extractor's `rev`. A first name that is a project-wide alias with two targets still silences the reference, unless a nested type of an enclosing type binds it.

**C# generic arity in type keys (added in 1.1.0).** C# looks a name with K type arguments up among the types with K type parameters only, so `Result<int>` never names a non-generic `Result` and a bare `Result` never names `Result<T>`. A C# type key now carries the arity the way the .NET reflection name writes it: `App.Result` for a non-generic type, ``App.Result`1`` for `Result<T>`, ``App.Outer`1+Inner`` for a type nested in a generic one. The C# extractor's `declarations()` writes these keys, and every reading of a use writes the arity of what it names: a generic name, an unbound name in `typeof` (`Repo<,>` is ``Repo`2``), each generic segment of a qualified name, a generic attribute (``Gen`1`` and ``GenAttribute`1``), a using alias target and a `using static` target. The `alias` fields of the extract's `scope` and the targets `collectGlobalUsingAliases` returns carry the arity too. A consumer that builds its `SymbolTable` from the extractor's declarations and resolves the extractor's hints needs no change. A consumer that reads a C# key as a type name sees the backtick and the arity of a generic type. An extract or a table stored by an earlier build is stale by the C# extractor's `rev`.

**C# `using static` (added in 1.1.0).** A C# `using static T;` imports the nested types of `T` and its extension methods, at the level of the body that holds the directive: the compilation unit (the last level of the lookup, with the plain usings, so a type of the global namespace or of an enclosing namespace still comes first and a plain using that imports a type of the same name makes the reference ambiguous), a namespace body (read at that namespace, before the next one outward), or the whole project for a `global using static`. The extractor declares each extension method under its class as well as under its namespace (`App.Ext.StringExt#Shout()` beside `App.Ext.Shout()`), so the directive imports the methods of its class alone. `CsharpGlobalFacts` gains the optional field `globalStatics`, the types of the file's own `global using static` directives (a type argument written as its arity, ``Repo`1``; the `scope.globalStatics` of the file's `CsharpExtract` lists them), `CsharpProjectScope` gains `statics`, the types of the whole project, and `CsharpUsesOptions` gains `projectGlobalStatics`, which a consumer fills from `CsharpProjectScope.statics` as it fills `projectGlobalUsings` from `usings`. A consumer that passes none sees the `using static` directives of each file only. `CsharpExtract.scope` gains `staticDecls`, each directive with its block, and the `outer` entries of a `target` descriptor keep the `global::` qualifier of a `statics` entry. An extract stored by an earlier build lacks them and is stale by the C# extractor's `rev`.

**C# file-local types (added in 1.1.0).** A C#11 `file` type, and a type nested in one, is not published, yet inside its own file its name binds it: a file-local type found at a lookup level removes the public types of that level (the C# 11 file-local types proposal), and a nested type is found before any namespace. The candidate group of a reference in that file ends at the reading that names such a type, so the public type of the same name in another file, in an outer namespace or behind a using is never reached, while the readings nearer than it (a nested type of an enclosing type, a type of an inner namespace) still bind. The same holds for the target of a using alias or a `using static` directive and for an alias-qualified name or attribute (`S::Helper`, `[S::Marker]`). Other files are not affected. `CsharpExtract` gains `fileLocalTypes`, the keys of the types the file declares but keeps to itself, written like declaration keys (`App.Helper`, `App.Outer+Inner`). An extract stored by an earlier build lacks it and is stale by the C# extractor's `rev`.

**C# base classes (added in 1.1.0).** C# reads the nested types of a type's base classes as members of that type, so inside `class MyHandler : HandlerBase` a bare `Options` names `HandlerBase.Options` before any `Options` of a namespace, and `Derived.Options` names the `Options` the base class of `Derived` nests. The C# extractor's `declarations()` now records the base list of every class, struct, record and interface: for each base, the key `base:<type key>`, a tab, and the value `<offset>:<name>`: where the base's name is written in its file, and the name with its type arguments as their arity (`global::` kept on a rooted name, `S::` on one led by a using alias). Every part of a partial type adds its own, and an interface also declares `interface:<type key>`. A file that records such a name declares its using directives once, as `usings`, a tab, and a JSON value, and the resolver reads the name with them as a reference in that file is read; a record holds no reading of its own, so the declared keys stay small. `SymbolTable.declare` keeps a key that holds a tab out of its names and lists it under the part before the tab; `SymbolTable.valuesOf(language, head)` returns each value with the files that declared it. A consumer must hand the table every one of these keys from every file that declares it, and that is a change for a consumer that keeps only some files per key. The key that needs it most is `usings`: it is recognised by its exact start, the six letters `usings` and a tab, and two files with the same using directives declare the very same key, so a table built from a store that kept the key for the first of them alone reads the bases and the member types of the other file with no using directive at all. Such a base then binds only what its own namespaces reach, the base class is not followed, and every reading that goes through it falls back to what it was before: a nested type of the base is not found, and an inherited member no longer silences a same-named type. The other keys with a tab (`base:`, `file-base:`, `members:`, `methods:`) name their type before the tab and are read once per file that declares them, each with that file's `usings`, so a file dropped from one of them drops that file's part of the type. Nothing else changes for a consumer that passes every declared key of every file to `declare`. A C#11 `file` type records its bases as `file-base:<type key>`, apart from a published type of the same name, and each record is read only for the `file` type of a file that declares it: a published type, or a `file` type of another file, may have the same full name and is another type. `TargetHint` (the `symbol` form) gains the optional field `within`, the key of a type whose body holds the reference: each nested reading of a C# candidate group carries it, and `makeResolver` reads such a reading in that type first and then in its base classes declared in the repository, nearest first. A `file` type of the referencing file is written `file:<type key>` there, and in the type lists of a `CsharpCondition`: `makeResolver` reads for it the `file-base:` records of the referencing file and nothing recorded under the published key (no base, nested type, member or method of a published type of that name), and for a published type no `file-base:` record. A dotted reading whose first names bind a type reads the rest the same way. An interface a class implements hands down no nested type, and an interface inherits those of its base interfaces. A base the declaring file reaches only through a project-wide `global using` of another file, a base that is itself a `file` type, and a base class outside the repository, are not followed: the reading stays what it was. The C# extractor's `rev` says so. `Classification` keeps its three answers and their meaning: `ambiguous` says the name is declared in more than one place and nothing else, so a consumer may go on counting it as that. On the two large C# repositories of the corpus the count of `ambiguous` answers is the same as before these changes, 179 on jellyfin and 7 on eShop. The declared keys of jellyfin grow from 163 KB to about 1.2 MB with the base, member, method and using records.

**C# attribute names (added in 1.1.0).** C# resolves `[Foo]` as `Foo` and as `FooAttribute`, each by itself, and takes the one that is an attribute class. The candidate group of a C# attribute is now one candidate whose optional field `attribute` (on the `symbol` form of `TargetHint`) holds the ordered group of each reading, `written` and `suffixed`; `suffixed` is absent when the written name already ends in `Attribute`. `makeResolver` binds each group by itself and asks the recorded base lists whether the class it binds derives from `System.Attribute`. A reading that binds such a class is the attribute. A class whose bases all lie in the repository and never reach `System.Attribute` gives no edge as an attribute, so a domain class `Route` beside the framework's `[Route]` stays silent. A class whose base leaves the repository under another name is taken as the suffixed reading, and as the written reading only where the written name ends in `Attribute`. Both readings binding attribute classes is the compiler's error CS1614 and gives no edge. Where a reading ends at a `file` type of the referencing file, the two readings stay one ordered group as before. The C# extractor's `rev` says so.

**C# instance methods before extension methods (added in 1.1.0).** C# turns to extension methods only when the receiver has no applicable instance method. The C# extractor's `declarations()` now lists the instance methods of each type other files can name: `methods:<type key>`, a tab, and one entry per overload, `<name>:<type parameters>:<required parameters>:<all parameters>` (the last `*` for a `params` list), marked `~` when protected and `-` when private, joined by spaces. A static method, an explicit interface implementation and an extension method are not listed, and a private method only in a `partial` type. Where the file writes the type of a call's receiver (a parameter, a field, a property or a local with a type of its own, `this`, or `this.field`), every reading of the extension call's candidate group carries the optional field `unless` (on the `symbol` form of `TargetHint`), a list of `CsharpCondition`. The one condition today, `instance-method`, holds the called name, the number of the call's arguments and of its written type arguments, the ordered group of readings of each written receiver type, the key of the enclosing type for a call on `this`, and the keys of the types around the call. It holds when the receiver's type, in any part, or a base class of it in the repository (for an interface, a base interface) declares an instance method of that name that the call fits by those counts and that the calling code can reach: a protected one from the declaring type and the types derived from it, and through an instance only when the instance's type is the calling type or derives from it, a private one from the declaring type alone. The interfaces a class implements are not read, as in the language: an explicit implementation and a default interface method are no members of the class. So `config.Get<T>(key)` still binds an extension `Get<T>` beside an instance `Get(key)`, and `item.Has(kind)` one beside an instance `Has(kind, index)`. Argument types are not read: where two overloads take the same counts, the instance method is taken. A reading whose condition holds binds nothing: `classify` answers `absent` for it, exactly as for a name the repository does not declare, and `resolve` and `resolveFile` answer nothing, so the group ends in silence and a consumer that counts `ambiguous` answers counts none for it. A receiver whose type the file does not write (`var`, a call result, an inferred lambda parameter) carries no condition. In a `CsharpExtract`, an extension call (an `ext` descriptor) names its receiver's written types by their places in the new top-level list `receiverTypes` (its field `on`), and the types around it by a place in the new top-level list `lists` (its field `from`), so calls on one declaration and calls in one type body share them; a call with no receiver type to ask is written as before, with none of this. The two lists are part of the extract as `refs` is: an extract holds each of them whenever one of its `refs` names a place in it, and leaves it out only when none does. A consumer that stores the extract stores `lists` and `receiverTypes` with `refs`; an extract stored by an earlier build is stale by the C# extractor's `rev`. Where a descriptor names a place the extract does not hold, `assembleCsharpCandidates` gives no candidate group for that call: it gives no edge, and nothing throws. The C# extractor's `rev` says so.

**C# members of the enclosing type (added in 1.1.0).** C# reads the members of the types around a simple name, inherited ones included and from every part of a partial type, before any namespace. `Settings.Get()` in a class that inherits a property `Settings`, or whose other part declares one, reads that property and no static class `Settings`. The C# extractor's `declarations()` now lists the members of a type that are no types (a field, a constant, a property, an event, a method, a record's primary constructor parameter): `members:<type key>`, a tab, and one entry per name joined by spaces, `<name>` or, for a field or a property whose written type is a named type, `<name>=<offset>:<type name>` in the form of a base record; a private member, and a primary constructor parameter of a class or a struct, is led by `-`. Only a type whose members other code can read by a simple name lists them: a `partial` type, an interface, and a class or a record that is neither static nor sealed; a private member is listed only in a `partial` type. A field or a property named as its own type (`public SourceType SourceType { get; }`) is not listed, because C# reads that name as the type wherever a type fits, so `SourceType.Library` keeps its edge. Inside a type that is `partial` or lists a base, every reading of a receiver's candidate group carries the condition `member` in its `unless` list (`CsharpCondition`): it holds, and the readings bind nothing, when the nearest type around the receiver that knows its first name has it as such a member, declared in any part or inherited from a base class in the repository. A private member of a base class is not seen there, a nested type found nearer still binds, and a type position (`Color _c;`) ignores members as the language does. Inside such a type, an extension call whose receiver's first name the file does not declare now gives a candidate group too, each reading under the condition `no-member`: the readings are read only when the name is such a member, and where the receiver is that member alone and its written type has an instance method the call fits, they are not. Inside a type that is neither `partial` nor lists a base nothing changes. In a `CsharpExtract`, a `receiver` descriptor names the types that can hold such a member by a place in the top-level list `lists` (its field `members`), and so does such an extension call (`member.types` of its `ext` descriptor). The list is stored with `refs`, as for an extension call's `from`: a receiver or a call that names a place the extract does not hold gives no candidate group, so no edge, and nothing throws. A reading whose condition holds answers `absent` from `classify`, never `ambiguous`. A consumer's graph can show new extension-method edges for calls on inherited members. A member inherited from a base class outside the repository (ASP.NET Core's `ControllerBase.User`) is a known limit: the repository holds no declaration to read, so a same-named type of the repository still gets the edge. The C# extractor's `rev` says so.

**Rust crate-root items (added in 1.1.0).** `use crate::Error;` names what the crate-root file binds as `Error`, and so does `use core_lib::Error;` in the root file of the path dependency `core_lib`; in an edition 2015 crate a `use` path is relative to the crate root, so `use Error;` names an item the crate-root file binds at its top level. Which names those are is read from the root file's parse tree, never from its text: the Rust extractor's `declarations()` now also declares, for every file, each name its top level binds as an item (an item it defines, the derive a function with `#[proc_macro_derive(Name, …)]` defines, beside that function's own name, an item of an `extern` block, a name a top-level `use` brings in, and the items of `thread_local!`, `lazy_static!`, `bitflags!` and `cfg_if!`) under the key `item:<name>`, and each name its top level binds with `extern crate` (the alias, else the crate) under the key `extern:<name>`, beside the keys it gave before, and the Rust extractor's `rev` says so. A name bound with `extern crate` is one a `crate::` path or a path into a dependency goes through (`pub extern crate inner as name;` in a facade), and no item an edition 2015 `use` path names. Which crate such a name stands for is declared under `extern:<name>=<crate>`: `extern crate a as b;` in a crate root makes `b` name the crate `a` in every module of that crate, in every edition, and when `a` is an in-repo path dependency, `use b::X;` binds its library. Written anywhere else, the declaration binds `b` in its own module or block only, and the extractor's `uses()` says so in the path it emits: the declaration itself is emitted as `extern::a`, a crate named for certain, and a `use` of that same scope that starts with `b` as `extern::a::as::b::X`, which is the crate from edition 2018 on and the path as written in edition 2015. `extern` is a keyword, so no path of the source starts with it. In edition 2015 a `use` path cannot start with a crate the root does not bind: its first segment is what the first crate root that binds it makes of it, a crate bound there with `extern crate` or a module or an item of that root. So `use util::slug;` names the root's `mod util;` where the package also has a path dependency `util`, and names nothing where the root has neither that module nor `extern crate util;`; the `extern crate util;` line itself binds the dependency wherever it stands.

`makeResolver` passes its `SymbolTable` to `resolvePathToFile` as an optional fifth argument (`ResolverDeps.resolvePathToFile` takes it), and the function `makeResolvePathToFile` returns reads that table for these questions and for the module declarations described next. It reads a crate root from the table alone and never from the root's text, so **the table must hold every key the extractor declares for every crate-root file**, each under that file: a table that keeps only some of the files of a key, or that leaves a root file out, loses the edges that go through that root. `use core_lib::Engine;` against a root's `pub use engine::Engine;` then gives no edge, and in an edition 2015 crate whose root file is not in the table every import of a path dependency gives none, because the `extern crate` that would bind it is not seen. A consumer that builds its table from every file's declarations and hands `makeResolvePathToFile`'s function to `makeResolver` needs no change; a consumer that compacts or filters its table must keep the keys of the crate roots whole. Called without any table, the function has no parse tree at all and answers as 1.0 did: it binds a root file for a `crate::` path or a path into a dependency when the file's text declares the name anywhere, which a word in a string or an item nested in a function also satisfies; it resolves a path dependency in edition 2015 as it does from 2018 on; and it knows no item of a root and no name bound with `extern crate`, so an edition 2015 `use` path of a root's own module and a path through an alias written in another file stay silent (an alias used in the scope that writes it binds without the table). A name the root defines only inside an inline `mod`, a function body, an initializer, a closure or a `macro_rules!` body, or through a macro whose expansion is not known, gives no edge; a root file the pass did not extract gives none either.

**Rust module declarations (added in 1.1.0).** A package can have several crate roots over one directory: `src/lib.rs` beside `src/main.rs`, a `[[bin]]` whose path lies in `src/`, or the binaries of `src/bin/` above a directory without a `main.rs`. Which of them compiles a module file is read from parse trees: the Rust extractor's `declarations()` now also declares, for every file, each module the file places in a file of its own by name alone. The key is `modfile:<path>` for a declaration nothing can switch off, and `modfile?:<path>` for one that a `cfg` may remove: a `cfg` on the `mod`, on an inline module around it, or at the head of that inline module or of the file. The path is the module's names from the declaring file's own module, joined by `/`: `modfile:x` for `mod x;`, `modfile:outer/x` for one inside the inline module `outer`. The Rust extractor's `rev` says so. Only a plain `mod x;` is declared: none with a `path` attribute, a `cfg_attr` or an attribute macro in front of it or around it, none inside a function body or a macro, and none from a file that does not parse to the end. The function `makeResolvePathToFile` returns follows these declarations from a file up to the roots, through the same table `makeResolver` passes. A root reached by `modfile:` declarations alone certainly compiles the file; a root reached through a `modfile?:` declaration compiles it in some configuration at most, and whether its `cfg` ever holds is not read. `crate::Item` binds the first root that holds the name, in this order: the root that certainly compiles the file, then the roots that may compile it under a `cfg`, then the other roots in the order they had in 1.0.0, the library first. Two or more roots that certainly compile the file give no edge for a root item; a root under a `cfg` is never one of the two. A root not reached is not ruled out, because a `path` attribute, `include!` or a macro can place a file anywhere. The edition of a file follows the same roots: an edition 2015 `use` path names an item of the roots reached when they are all edition 2015, or of the library and `src/main.rs` when those are, and never an item of a root with another edition. Called without the table, the function knows no declaration and keeps the order of 1.0.0 for every file; a file in a directory of `src/bin/` without a `main.rs` then has no known crate, and its `crate::` paths give no edge. A consumer that builds its table from every file's declarations needs no change.

**TypeScript and JavaScript call forms (added in 1.1.0).** A `require('x')` call, an `import x = require('x')` and a dynamic `import('x')` read the `require` or `import` condition of a package's `exports` and `imports` by their own form, as TypeScript resolves them, where an `import` or `export` statement and an import type (`typeof import('x')`, `import('x').T`) read the condition of their file's format. A dynamic `import('x')` reads `import` except where the compiler emits it as a `require`: under a `module` that is neither a Node one nor `preserve`, in a file emitted as CommonJS (a `.cts` or `.cjs` file, and any other file under `module` commonjs, amd, umd, system or none), it reads `require`. An import type is told from a call by where it stands. The extractor reads the type nodes of the grammar (an annotation, a type argument, a type predicate, `typeof`, a union, a conditional or `readonly` type, the right side of `as`, `satisfies` and a type alias), and the places the grammar parses as expressions instead, which it recognises by their shape: the type argument of a class heritage clause, a call, a tagged template or a `new` (`Base<import('x').T>`), `keyof import('x').T`, a parenthesized type, and a template literal type. The heritage clause of an interface (`extends`) and a class's `implements` clause hold expressions to the compiler too, so an `import('x')` there is a dynamic import call, as the compiler resolves it. Known limits: `export interface I extends import('x').T {}` gives no edge, because the grammar's recovery from it loses the specifier; and a type spelling the grammar cannot read that is not in the list above keeps the call form of a dynamic `import()`, as does one that follows another the grammar cannot read in the same run of statements, since its recovery can run on into the next statement. The TypeScript extractor's `uses()` therefore marks those three forms: the `path` form of `TargetHint` gains the optional field `callForm`, `'require'` or `'import'`, absent on every statement that names no mode itself. The `resolution-mode` import attribute names one: a type-only import or re-export (`import type { T } from 'x' with { 'resolution-mode': 'import' }`, `export type { T } from 'x' with { … }`) and an import type (`import('x', { with: { 'resolution-mode': 'import' } }).T`) read the condition the attribute names, whatever the format of their file, as the compiler reads them. Their hint carries `callForm` `'require'` when the attribute says `require`, and the third value `'esm'` when it says `import`: the `import` condition under every setting, where `'import'` is a dynamic `import()` the compiler may emit as a `require`. The attribute on a value import, on an import with an inline `type` specifier or in the options of a dynamic `import()` decides nothing, as in the compiler. `ResolverDeps.resolvePathToFile` takes the hint's `callForm` as an optional sixth argument, and the function `makeResolvePathToFile` returns reads it for TypeScript and JavaScript files only. A consumer that builds its pass from the extractor's hints and hands `makeResolvePathToFile`'s function to `makeResolver`, as both consumers named in the table do, needs no change; a consumer that stores hints stores the field, and one stored by an earlier build is stale by the TypeScript extractor's `rev`. A file no tsconfig covers is read with the conditions Node and TypeScript enter by default, and a `types@<range>` key is entered when TypeScript 6.0.3 satisfies the range. A tsconfig that extends a preset Runes cannot read (a package that is installed and not in the repository, as every package is when the consumer excludes `node_modules` or resolves through a `FileView` of the commit) inherits a `module`, a `moduleResolution` and `customConditions` that are unknown wherever the config and its readable bases do not set them. The unknown ones are taken to be values the compiler accepts beside the known ones: a Node `module` goes only with a Node resolution, and Bundler only with `commonjs`, an ES kind from `es2015` on or `preserve`. The lookup is read once for each pairing that remains, and with a non-standard key both entered and passed over; it binds the file all of those readings name, and where they differ the first listed target that one of them names. So a `require()` call, an `import x = require()`, a `.mts` or `.mjs` file, an import outside an `import()` in a `.cts` or `.cjs` file, and any file of a config that sets a Node resolution or a `module` of `commonjs`, an ES kind or `preserve` itself bind as the compiler binds them with the preset installed, as long as no non-standard key (`browser`, `react-server` or a custom one) is listed before the branch. An `import()` in a `.cts` or `.cjs` file of a config that sets neither, and a config whose own `module` is `amd`, `umd`, `system` or `none`, fall back to the first listed target.

## `@chrisdudek/runes/mcp`
