# Runes 1.x: the stable API

This is what `@chrisdudek/runes` promises under semantic versioning from 1.0.0 on. A name listed here keeps its meaning and its signature for every 1.x release: a minor release may add names, options and fields, a patch release fixes behaviour to match what the README says, and anything that breaks a listed name waits for 2.0.0. A test (`test/exports.test.mjs`) holds this page and the package's exports together both ways, so a name exported without being listed here, or listed without being exported, fails the build.

## What the promise covers

- **The names below**, from the six subpaths, with the behaviour the README documents for them. Types are part of it: a type listed here keeps its fields (a minor release may add optional ones).
- **The module files a vendoring consumer imports** without going through an index: `dist/version.mjs`, `dist/<subpath>/index.mjs` for each subpath, and in the test kit `dist/testkit/parity.mjs`, `dist/testkit/measure.mjs`, `dist/testkit/client.mjs` and `dist/testkit/runtime/index.mjs`, each with the names it exports today. A vendored copy takes whole directories or these files, so these paths are the vendoring surface; every other file under `dist/` may move in any release, and `dist/fs/` is not a subpath (see below).
- **The documents and formats**: the `<tool>-error/1` error document; the grammar manifest (`grammars/manifest.json`, its schema id); the vendoring pin (`runes.pin.json`), the commands, options and exit codes of `tools/vendor.mjs`, and the skill fragment names and markers.
- **The MCP wire shape** the adapter generates: tool names, one field per argument and flag with its type, which fields are required, what the annotations mean, one JSON block with notes in `_meta`, -32602 for input that does not fit, cancellation and time limits.

## What it does not cover

- Every export of an internal module. The per-language extractors by name (all but `csharpExtractor`; `extractorForLanguage` is the promised way to one), the in-process MCP executor, the git test environment (`gitEnv`, `makeTempRepo`), the per-language resolution helpers, the table's helper functions, the command-line parser, the error document and the one-block `--json` rule, the usage-text reader, the guard's scanner and the git environment's constants stay in their modules for Runes' own code and tests; they may change in any release.
- The file-system code under `dist/fs/` (the cross-process lock, atomic writes, the repository root). It ships and is tested, but no subpath exports it and no family tool uses it yet; it may change in any release until a 1.x minor exports it for a tool that adopts it.
- Wording: error messages, tool and field descriptions, report lines. Codes (`code` in the error document, `ELOCKED`, `ELOCKBREAK`, `EPARSESTOPPED`, `ERUNTIMEABORTED`, `usage`, and `config-unreadable` and `package-entry-missing` of a relation diagnostic) are stable; sentences are not.
- The shape of the per-language extract records: `CsharpExtract` with its `scope` and its descriptors (`CsharpRefDescriptor`), the C# project facts (`CsharpGlobalFacts`, `CsharpProjectScope`), and the per-file keys an extractor's `declarations()` writes (the C# `base:`, `members:` or `methods:` records, the Rust `mod:` or `glob:` keys, and the others below). They follow their extractor's `rev` and may change shape in a minor release, a field or a descriptor kind included, so a consumer that stores them extracts again when the `rev` changes. The functions that produce and read them keep their signatures.
- The exact edges an extractor finds. An extractor fix changes what it reports for some source, in a minor or a patch release; the extractor's `rev` changes with it, so a consumer's cache keyed by `rev` drops what it computed before. The relation catalogue (`reference/relations/`) is the specification that fixes move towards.

The Consumers column names the family tools that import each name on their `release/6.1.0` branches (sources and tests; a vendored copy counts), found by reading their imports. 1.0.0 promises only what a family tool imported when it was written, and a 1.x minor adds a name, additively, when a tool adopts it. Two value exports, `toolName` and `startMcpClient`, were imported only by Horde, which has since left the family; they stay exported and promised, and carry "—" until a tool imports them.

A type marked "—" is imported by no tool and is kept because a kept export's signature reaches it: it is a parameter, a return value or a field of one, so without its name a TypeScript consumer could not write down what it passes to or gets back from a promised function (`TreeSitterRuntime` is what `ParserHostOptions.runtime` takes, `PrepareResult` what `ServerOptions.prepare` returns). Its fields are promised through that signature whether or not the name is exported, so exporting the name adds no promise; the per-language extract records are the exception, as the list above says. A type reached only through a removed name went with it (`InProcessExecutor`, `CallContext`, `GitEnvOptions`, `TempRepo`).

`version` (the package version, the same value on each subpath that has it) is exported by `relations`, `ast` and `grammars`, where Yggdrasil reads it: it keys its relation cache on the `relations` one and pins all three against its dependency. `cli`, `mcp` and `testkit` export none, since no tool reads one there; a vendoring consumer that wants the version reads `RUNES_VERSION` from `dist/version.mjs`.

**The file view (added in 1.1.0).** Resolution reads the repository: whether a candidate file exists, which files a directory holds, the text of a `tsconfig.json`, a `package.json`, a `Cargo.toml`, a `go.mod`, a `composer.json`, a `compile_commands.json` or a `.csproj`, which Python manifests (`pyproject.toml`, `setup.cfg`, `setup.py`) a directory holds, and the text of the first two for the source roots they name (see "Python source roots from configuration"); `setup.py` is code and its text is not read. By default it reads the disk under the project root, as 1.0.x did, and a consumer that passes nothing sees no change. A consumer that resolves the contents of one commit passes `makeResolvePathToFile(projectRoot, ownerOf, isExcluded, { files })` (and `buildCsharpProjectScopes(projectRoot, facts, { files })`) with a `FileView`, so an untracked or ignored file on disk (build output, a generated config, an installed package) cannot decide where an import lands, and the same commit gives the same edges on every machine. `FileView` has five methods (`exists`, `isFile`, `isDirectory`, `list`, `read`) over POSIX paths relative to the project root, `''` being the root. `listedFileView(paths, read)` builds one from a list of file paths (the directories are the ones the list implies) and a reader for their text: anything not listed does not exist, so a symbolic link is absent unless it is listed, there is no `node_modules` unless it is listed, and names are compared exactly. Runes spawns no git and makes no decision about what "the commit" is: the consumer supplies the list and the reader. `isExcluded` keeps its meaning on top of the view. Every read of every language's resolver goes through the view; with a view given, the disk is not touched, and an exception the view's `read` throws reaches the caller of the resolver. A consumer chooses the view: it can pass the files git would commit, the files of `HEAD`, or any list it holds.

**C# reachability (added in 1.1.0).** C# binds a name only to a declaration of its own compilation or of an assembly the compilation references, and the extractors read one file at a time, so every in-repository declaration of a name was a candidate, including an extension method or a type of a project the calling project cannot see: a false relation that no declared relation could answer. `buildCsharpReachability(projectRoot, csFiles, { files })` reads the reference graph of the repository's projects and returns a `Reachability`, a function `(fromFile, targetFile)` answering `'same'` (one project), `'reachable'` (the target's project is in the caller's closure), `'unreachable'` or `'unknown'` (the graph can say nothing: a file with no project facts, or a caller that reaches an open project); a consumer passes it as `ResolverDeps.reach` to `makeResolver`. With `reach` given, a symbol hint of a C# file loses every definer in a project its project cannot reach before the owners are counted, and when a definer lies in the file's own project only that project's definers stay (the compiler prefers a type of its own compilation to a referenced one of the same name; an extension method has no such preference, the compiler chooses among them by overload resolution); `unknown` filters nothing; the global `Program`, declared (`public partial class Program { }`) or synthesized from top-level statements, is one name to the compiler, so when the graph says something about every definer of it the two kinds are chosen among together (the one in reach, or silence when two referenced projects each have one), and when it can say nothing about one of them the order of a pass without a graph stays: the declared class first; `resolve`, `classify` and `resolveFile` all apply it, and the path axis and every other language are untouched. A reference graph is read from the project files (`*.csproj`, and `*.fsproj` and `*.vbproj` a chain passes through) and every `Directory.Build.props` and `Directory.Build.targets` above them: `ProjectReference` (a path, read against the file that holds it and, in an imported file, against the project too; a wildcard; `$(MSBuildThisFileDirectory)` and `$(MSBuildProjectDirectory)`), `Reference` by name, by the file name of an `Include` that is the assembly's path, or by `HintPath` file name (the child element or the attribute), and `PackageReference`, the last two against the assembly names (set in a project file or in a `Directory.Build.*` file) and package ids of the repository's own projects; every directory and file name of a path is matched in any case; references are transitive, conditions are read and never evaluated (a raw `>` inside a quoted condition ends no tag, wherever the condition stands among the attributes), and an imported file the view holds is read too. A file of a project's directory that a `<Compile Remove>` of the project takes out (and no `<Compile Include>` of it names again) is in no compilation of that project: as a target it is `unreachable` from every file, its own project's included, and as a caller it is `unknown`; a removal under a condition (its value may hold a raw `>`) or inside a target is not read, because it may not apply, and a project with a `<Compile Include>` whose path needs a property this reader does not know keeps every file, because that include may put any of them back. Everything unknown fails open: a project with a reference path that needs another property or names no file of the repository, a `Compile` item whose path needs another property or leaves the repository, an unresolvable import, an unconditional import of a file the view does not hold or a shared-project import is open and reaches everything, and so is every project that reaches an open one; a file that another project links through a `Compile` item outside that project's directory is code of that project too, and the link adds that file to it and nothing else: as a caller the file sees what that project references, as a target it is seen by that project (`same`) and by every project that reaches it, and a linked file under no project file belongs to the projects that link it alone; a file under no project file, or not among `csFiles`, is reachable from and to everything. The worst case is therefore the answer without `reach`, and a consumer that passes nothing sees no change. A `Reachability` built here also answers `internalsVisible(fromFile, targetFile)`, an optional member of the type: true when the two files share a compilation, or when a compilation of the target that the caller reaches names the caller's assembly (its project file's name, its `<AssemblyName>` or its `<PackageId>`) as a friend, through an `<InternalsVisibleTo Include>` item (`$(MSBuildProjectName)` and `$(AssemblyName)` read as the defining project's names), an `<AssemblyAttribute Include="…InternalsVisibleTo">` item, or an `[assembly: InternalsVisibleTo("…")]` attribute in a C# file the project compiles (read only when a caller first asks about that project); a grant it cannot name (an unknown property, a constant) names every project, and a pair the graph knows nothing about is visible. The C# extractor declares a type or an extension method that only its own assembly sees (`internal`, `private`, a top-level type with no access modifier, a type nested in one of those, an extension method that is not public or whose class is not; a `partial` part without an access modifier is not marked by its own file) a second time under the marker key `internal:<key>`, which no C# name can produce, so it never binds a reference. The parts of a partial type are one type with one accessibility, so `makeResolver` reads an unmarked declaration of a type as internal too where another file of the same compilation (`reach` answers `'same'`) marks that type or a type around it: `partial class Order` beside `internal partial class Order` is internal. With `reach` given and answering `internalsVisible`, a definer in a reachable project of another compilation whose declarations of the name all carry the marker is dropped for a caller that is not a friend; a `Reachability` without the member drops none. `csFiles` is the repository-relative C# files the pass holds, `files` the same `FileView` the other readers take (without it the disk under `projectRoot` is read).

**Unreadable configuration (added in 1.1.0).** `ResolvePathOptions.onDiagnostic` receives a `RelationDiagnostic` (`code`, `file`, optional `line` and `column`, `message`) when resolution consults a configuration file it cannot read, so an absence of edges under it is no longer silent. It is called synchronously, at most once per `(code, file)` for one resolver, and only for a file resolution actually consulted. Of the two codes today, `package-entry-missing` is described below and `config-unreadable` is for a `tsconfig*.json`, `jsconfig*.json`, `package.json`, `composer.json` or `compile_commands.json` that does not parse and for a `pnpm-workspace.yaml` whose `packages:` list cannot be read; `file` is the repository-relative path, and `line` and `column` (1-based) are where the failure lies in the file as written, comments and trailing commas included, counted from after a byte order mark as an editor shows it. A position is given when the JSON parser names one, when the input ends too soon (the end of the file), or when the parser names none but the offending token is unambiguous (a single-quoted string, an unquoted value, `undefined`, or a whitespace character JSON does not allow such as a no-break space), and then it is that token. Where the parser quotes a character that is not the one Runes finds (a structural character where a value belongs: `{"a": }`, `[1,,2]`, a trailing comma in strict JSON, `{"a": : 1}`), `line` and `column` are absent and the message names none: the file is reported without a position, never with a guessed one. Lines end at LF, CR or CRLF. `code` is a `string` and stays stable; `message`, `line` and `column` are best effort and not part of the promise. A tsconfig, jsconfig, package.json, composer.json or compile_commands.json with a byte order mark reads fine and never reports. What a consumer does with a diagnostic is its own: it can show it as a warning, put it in a report, or ignore it. Resolution is unchanged: an unreadable file still governs nothing; the callback only makes that visible. The Cargo, `go.mod` and project-file readers take their lines as they find them and never fail to parse, so they report nothing.

**Package entries under build output (added in 1.1.0).** A package whose `exports`, `types`, `typings`, `module` or `main` names a file that is not in the repository (build output a clean checkout does not hold) is read through the package's own TypeScript project: every `tsconfig.json` and `tsconfig.*.json` directly in the package directory whose `outDir` holds the entry (for a declaration, its `declarationDir` when set) maps it back to the source under `rootDir`, so `dist/a/b.js` and `dist/a/b.d.ts` name `src/a/b.ts` or `src/a/b.tsx`, `.mjs` and `.d.mts` a `.mts` file, `.cjs` and `.d.cts` a `.cts` file, and a JavaScript source counts under `allowJs`. A dual package that a bundler builds (tsup, unbuild) names its two builds by format, `dist/index.mjs` with `dist/index.d.mts` and `dist/index.cjs` with `dist/index.d.cts`, all from `src/index.ts`: where no `.mts` or `.cts` source of that name is there, such an entry names the `.ts` or `.tsx` source. Without `rootDir` the root is the one the compiler computes, the common directory of the project's sources or the tsconfig's directory, and both are tried. A reading counts when it names a file the project holds, and all readings that count must name one file; otherwise nothing binds. A tsconfig that sets `noEmit` or holds no source writes no output and is not asked. An entry that is in the repository is the target as before, so the answer is the same before and after a build only when the consumer passes ignored output as excluded or resolves through a `FileView` of the commit. When an entry names no file and gives no source (no tsconfig maps it, or the tsconfigs map it to different sources, and the message says which), and nothing else binds the import, `onDiagnostic` receives `package-entry-missing` once per package: `file` is the package's `package.json`, the message names the entry, and there is no `line` or `column`. It is sent for the first import that binds nothing for this reason, and the message names the entry that import reached; an import of the same package that reaches another entry (another `exports` subpath or condition) may still resolve. A consumer may show it as a warning that an import reaching that entry is not resolved.

**Same-package references (added in 1.1.0).** The Java and Kotlin extractors now give a candidate group for a simple type name written without an import, because a type of the package is in scope in every file of the package (in Kotlin after an explicit import or alias, and before a star import and the default imports; a capitalised callee such as `Owner(...)` counts as well as a receiver, and a lowercase name is never read). The group holds, in order, the member types a supertype of an enclosing declaration may inherit (`<package>.<Super>+<Name>`) and then `<package>.<Name>`, both symbol hints resolved through the shared JVM namespace, so a Kotlin class of the package counts too. `TargetHint` (the `symbol` form) gains the optional field `samePackage`: `true` marks a key that names a type of the referencing file's own package, and `makeResolver` then lets the file see only the definers its source set can see. For the Maven and Gradle layout `<module>/src/<set>/java|kotlin/…`, code of a main-like set (`main`, a variant such as `debug`) never sees a class of a test-like set (`test`, `testFixtures`, `integrationTest`, `it`, `jmh`, `androidTest`, a multiplatform `…Test`), whichever module holds it; a test-like set sees main-like sets, its own set and the `testFixtures` of any module, and not another test-like set of its own module. A path outside that layout counts as visible. A hint without the field resolves as before, and a consumer that passes hints through `makeResolver` needs no change. The same-package group is not emitted where the simple name means something else (a type parameter in scope, a type the file declares, an import of that name or an alias for it, for a receiver a variable of that name), and a file of the unnamed or root package gives none; neither does a Kotlin file whose declarations could not all be read. Known limits, each with a catalogue case or a note: a member type inherited from a supertype outside the repository (or from a supertype's own supertype) is not known; a capitalised field (Java) or property or function (Kotlin) of that name that a static on-demand import or a supertype brings obscures a receiver and is not seen. What a consumer's graph now shows: a test that uses a class of its own package depends on the component that holds that class, so a graph that keeps tests and production code in separate components needs that relation declared. In Java, the group of a simple name that `java.lang` holds (`String`, `Override`, `Exception`; the public top-level types of `java.lang` in any JDK from 8 to 25) ends with the reading `java.lang.<Name>`, without `samePackage`, as Java reads such a name through the implicit on-demand import of `java.lang` after the package: it binds only a repository that declares `java.lang` itself, and otherwise lets `classifyUse` say the use leaves the repository. A Java type written `Outer.Inner`, whose first name is a type of the package written without an import, gives one group: each reading of `Outer` with the rest as its member types (`<package>.Outer+Inner`, an inherited `<package>.<Super>+Outer+Inner`, `java.lang.Thread+State`), then the name as written; a first name the file imports or declares, and a package-led name, stay one reading as written. The Java extractor's `rev` moves with each. In Kotlin, the group of a simple name that a default import holds ends the same way with that reading, after the package: the type names of kotlin.*, kotlin.annotation.*, kotlin.collections.*, kotlin.io.*, kotlin.ranges.*, kotlin.sequences.*, kotlin.text.* and kotlin.jvm.* (`kotlin.String`, `kotlin.collections.List`, `kotlin.jvm.Throws`), and else of `java.lang` (`java.lang.Thread`), so `classifyUse` says such a use leaves the repository; a lowercase call such as `listOf(...)` gives no use. The reading of a simple name as a type of the file's own package gains the optional field `onDemand` (on the `symbol` form of `TargetHint`), the packages or types of the file's on-demand (star) imports, which Java reads after the package and Kotlin after the package and before its default imports. `classify`, `resolve` and `resolveFile` never read it, so no edge changes; `classifyUse` does: where a starred package or type of the repository declares the name, the use is the repository's and answers `unfollowed`, never `outside`, whatever a default import holds. The Kotlin extractor's `rev` moves with it, and the Java one with the field.

**C# using directives by namespace block (added in 1.1.0).** A plain C# `using N;` inside a namespace block now reaches only the references of that block and of the blocks nested in it. It is read at its block's namespace, before the next namespace outward. The namespace it names is read where it stands: `using Core;` inside `namespace A` names `A.Core` when the repository declares that namespace. `TargetHint` (the `symbol` form) and `SymbolSetMember` gain the optional field `shadow`, a list of dotted names. When the repository declares one of them, as a type or as a namespace some declared key lies in, `makeResolver` treats the reading as absent and goes on to the next candidate. A hint without the field resolves as before. `SymbolTable` gains `hasNamespace(language, name, accept?)`, true when some declared key of that language lies inside the dotted namespace `name`; with `accept`, a function of a file path, only the files it accepts count, and `makeResolver` passes one that drops the files `reach` answers `'unreachable'` for the referencing file, so a nearer namespace only a project out of the caller's reach declares does not hide a reading (it is no namespace to that compilation); without `reach` the question is as before. `CsharpExtract` changes shape: `scope.prefixDecls` lists each plain using with its block, the `target` and `ext` descriptors carry `at`, and each `outer` entry of a `target` descriptor carries `statics`. A consumer that stores the extract stores these fields too; an extract stored by an earlier build is stale, and the C# extractor's `rev` says so. `scope.aliasDecls` lists each using alias with its block in the same way. A using written after `global::` (`using global::Core;`) names the global namespace `Core` only, and the extract keeps that form: an entry of `scope.prefixDecls` holds the namespace without the qualifier and `rooted: true`, and the `prefixes` of an `outer` entry keep the namespace as written, `global::Core`. `scope.prefixes` still lists the namespace of every plain using without its block; the extractor no longer reads it, and it stays because a consumer that stores the extract reads it. The `target` descriptor has no `nearest` field: an earlier build of the 1.1.0 branch had one, and an extract stored by that build is stale by its `rev`.

**C# nested types of the enclosing types (added in 1.1.0).** C# reads the nested types of each type around a simple name, innermost type first and from every part of a partial type, before any namespace, alias or using. Inside `CreateOrder.Handler`, `Command` names `CreateOrder.Command`, not a `Command` of an enclosing namespace or an import. The C# candidate group of a simple or dotted name written inside a type now starts with one reading per enclosing type, `<namespace>.<Outer>+<Name>`, innermost first; a dotted `X.Y` reads `<Outer>+X.Y`, which the resolver binds as the nested `<Outer>+X+Y`. The nested readings apply inside a type's body only: its attributes, its base list and its constraint clauses lie outside it (C# spec §7.7.1), so `class Handler : Command { class Command { } }` derives from the `Command` around it. The `plain`, `attr` and `receiver` descriptors of `CsharpExtract` gain the optional field `types`, the declaration keys of the types whose bodies hold the reference, innermost first (`['App.Web.CreateOrder+Handler', 'App.Web.CreateOrder']`); it is absent outside every type body and on a `global::` reference. An extract stored by an earlier build lacks the field and is stale by the C# extractor's `rev`. A first name that is a project-wide alias with two targets still silences the reference, unless a nested type of an enclosing type binds it.

**C# generic arity in type keys (added in 1.1.0).** C# looks a name with K type arguments up among the types with K type parameters only, so `Result<int>` never names a non-generic `Result` and a bare `Result` never names `Result<T>`. A C# type key now carries the arity the way the .NET reflection name writes it: `App.Result` for a non-generic type, ``App.Result`1`` for `Result<T>`, ``App.Outer`1+Inner`` for a type nested in a generic one. The C# extractor's `declarations()` writes these keys, and every reading of a use writes the arity of what it names: a generic name, an unbound name in `typeof` (`Repo<,>` is ``Repo`2``), each generic segment of a qualified name, a generic attribute (``Gen`1`` and ``GenAttribute`1``), a using alias target and a `using static` target. The `alias` fields of the extract's `scope` and the targets `collectGlobalUsingAliases` returns carry the arity too. A consumer that builds its `SymbolTable` from the extractor's declarations and resolves the extractor's hints needs no change. A consumer that reads a C# key as a type name sees the backtick and the arity of a generic type. An extract or a table stored by an earlier build is stale by the C# extractor's `rev`.

**C# `using static` (added in 1.1.0).** A C# `using static T;` imports the nested types of `T` and its extension methods, at the level of the body that holds the directive: the compilation unit (the last level of the lookup, with the plain usings, so a type of the global namespace or of an enclosing namespace still comes first and a plain using that imports a type of the same name makes the reference ambiguous), a namespace body (read at that namespace, before the next one outward), or the whole project for a `global using static`. The extractor declares each extension method under its class as well as under its namespace (`App.Ext.StringExt#Shout()` beside `App.Ext.Shout()`), so the directive imports the methods of its class alone. `CsharpGlobalFacts` gains the optional field `globalStatics`, the types of the file's own `global using static` directives (a type argument written as its arity, ``Repo`1``; the `scope.globalStatics` of the file's `CsharpExtract` lists them), `CsharpProjectScope` gains `statics`, the types of the whole project, and `CsharpUsesOptions` gains `projectGlobalStatics`, which a consumer fills from `CsharpProjectScope.statics` as it fills `projectGlobalUsings` from `usings`. A consumer that passes none sees the `using static` directives of each file only. `CsharpExtract.scope` gains `staticDecls`, each directive with its block, and the `outer` entries of a `target` descriptor keep the `global::` qualifier of a `statics` entry. An extract stored by an earlier build lacks them and is stale by the C# extractor's `rev`.

**C# file-local types (added in 1.1.0).** A C#11 `file` type, and a type nested in one, is not published, yet inside its own file its name binds it: a file-local type found at a lookup level removes the public types of that level (the C# 11 file-local types proposal), and a nested type is found before any namespace. The candidate group of a reference in that file ends at the reading that names such a type, so the public type of the same name in another file, in an outer namespace or behind a using is never reached, while the readings nearer than it (a nested type of an enclosing type, a type of an inner namespace) still bind. The same holds for the target of a using alias or a `using static` directive and for an alias-qualified name or attribute (`S::Helper`, `[S::Marker]`). Other files are not affected. `CsharpExtract` gains `fileLocalTypes`, the keys of the types the file declares but keeps to itself, written like declaration keys (`App.Helper`, `App.Outer+Inner`). An extract stored by an earlier build lacks it and is stale by the C# extractor's `rev`.

**C# base classes (added in 1.1.0).** C# reads the nested types of a type's base classes as members of that type, so inside `class MyHandler : HandlerBase` a bare `Options` names `HandlerBase.Options` before any `Options` of a namespace, and `Derived.Options` names the `Options` the base class of `Derived` nests. The C# extractor's `declarations()` now records the base list of every class, struct, record and interface: for each base, the key `base:<type key>`, a tab, and the value `<offset>:<name>`: where the base's name is written in its file, and the name with its type arguments as their arity (`global::` kept on a rooted name, `S::` on one led by a using alias). Every part of a partial type adds its own, and an interface also declares `interface:<type key>`. A file that records such a name declares its using directives once, as `usings`, a tab, and a JSON value, and the resolver reads the name with them as a reference in that file is read; a record holds no reading of its own, so the declared keys stay small. `SymbolTable.declare` keeps a key that holds a tab out of its names and lists it under the part before the tab; `SymbolTable.valuesOf(language, head)` returns each value with the files that declared it. A consumer must hand the table every one of these keys from every file that declares it, and that is a change for a consumer that keeps only some files per key. The key that needs it most is `usings`: it is recognised by its exact start, the six letters `usings` and a tab, and two files with the same using directives declare the very same key, so a table built from a store that kept the key for the first of them alone reads the bases and the member types of the other file with no using directive at all. Such a base then binds only what its own namespaces reach, the base class is not followed, and every reading that goes through it falls back to what it was before: a nested type of the base is not found, and an inherited member no longer silences a same-named type. The other keys with a tab (`base:`, `file-base:`, `members:`, `methods:`, `shapes:`) name their type or extension key before the tab and are read once per file that declares them, each with that file's `usings`, so a file dropped from one of them drops that file's part of the type. One key without a tab is read per file as well, the mark `file-interface:<type key>` of a `file` interface: it is read only for the file that declares it, so a consumer keeps it for every file too, or a `file` interface of a dropped file is read as a class. Nothing else changes for a consumer that passes every declared key of every file to `declare`. A C#11 `file` type records its bases as `file-base:<type key>`, apart from a published type of the same name, and each record is read only for the `file` type of a file that declares it: a published type, or a `file` type of another file, may have the same full name and is another type. `TargetHint` (the `symbol` form) gains the optional field `within`, the key of a type whose body holds the reference: each nested reading of a C# candidate group carries it, and `makeResolver` reads such a reading in that type first and then in its base classes declared in the repository, nearest first. A `file` type of the referencing file is written `file:<type key>` there, and in the type lists of a `CsharpCondition`: `makeResolver` reads for it the `file-base:` records of the referencing file and nothing recorded under the published key (no base, nested type, member or method of a published type of that name), and for a published type no `file-base:` record. A dotted reading whose first names bind a type reads the rest the same way. Three more readings treat a `file` type as the type of its file it is: a `file` interface declares `file-interface:<type key>`, read for its own file alone, so it inherits the nested types of its base interfaces as a published interface does; a dotted name that leads through a `file` type of the file to a name that type does not declare (`Worker.Options` through `file class Worker : WorkerBase`) gives one more reading, `<key>+Options` with `within: file:<key>`, which finds the nested type the base class declares, where the group used to end with nothing; and an extension call whose receiver's written type is a `file` type carries it in the `instance-method` condition's optional field `fileReceivers` (the readings nearer than the `file` type, and the type as `file:<key>`), so an instance method the type inherits takes the call. An interface a class implements hands down no nested type, and an interface inherits those of its base interfaces. A base the declaring file reaches only through a project-wide `global using` of another file, a base that is itself a `file` type, and a base class outside the repository, are not followed: the reading stays what it was. The C# extractor's `rev` says so. `Classification` keeps its three answers and their meaning: `ambiguous` says the name is declared in more than one place and nothing else, so a consumer may go on counting it as that. On the two large C# repositories of the corpus the count of `ambiguous` answers is the same as before these changes, 179 on jellyfin and 7 on eShop. The declared keys of jellyfin grow from 163 KB to about 1.2 MB with the base, member, method and using records.

**C# attribute names (added in 1.1.0).** C# resolves `[Foo]` as `Foo` and as `FooAttribute`, each by itself, and takes the one that is an attribute class. The candidate group of a C# attribute is now one candidate whose optional field `attribute` (on the `symbol` form of `TargetHint`) holds the ordered group of each reading, `written` and `suffixed`; `suffixed` is absent when the written name already ends in `Attribute`. `makeResolver` binds each group by itself and asks the recorded base lists whether the class it binds derives from `System.Attribute`. A reading that binds such a class is the attribute. A class whose bases all lie in the repository and never reach `System.Attribute` gives no edge as an attribute, so a domain class `Route` beside the framework's `[Route]` stays silent. A class whose base leaves the repository under another name is taken as the suffixed reading, and as the written reading only where the written name ends in `Attribute`. Both readings binding attribute classes is the compiler's error CS1614 and gives no edge. Where a reading ends at a `file` type of the referencing file, the two readings stay one ordered group as before. The C# extractor's `rev` says so.

**C# instance methods before extension methods (added in 1.1.0).** C# turns to extension methods only when the receiver has no applicable instance method. The C# extractor's `declarations()` now lists the instance methods of each type other files can name: `methods:<type key>`, a tab, and one entry per overload, `<name>:<type parameters>:<required parameters>:<all parameters>` (the last `*` for a `params` list), marked `~` when protected and `-` when private, joined by spaces. A static method, an explicit interface implementation and an extension method are not listed, and a private method only in a `partial` type. Where the file writes the type of a call's receiver (a parameter, a field, a property or a local with a type of its own, `this`, or `this.field`), every reading of the extension call's candidate group carries the optional field `unless` (on the `symbol` form of `TargetHint`), a list of `CsharpCondition`. The one condition today, `instance-method`, holds the called name, the number of the call's arguments and of its written type arguments, the ordered group of readings of each written receiver type, the key of the enclosing type for a call on `this`, and the keys of the types around the call. It holds when the receiver's type, in any part, or a base class of it in the repository (for an interface, a base interface) declares an instance method of that name that the call fits by those counts and that the calling code can reach: a protected one from the declaring type and the types derived from it, and through an instance only when the instance's type is the calling type or derives from it, a private one from the declaring type alone. The interfaces a class implements are not read, as in the language: an explicit implementation and a default interface method are no members of the class. So `config.Get<T>(key)` still binds an extension `Get<T>` beside an instance `Get(key)`, and `item.Has(kind)` one beside an instance `Has(kind, index)`. Where two overloads take the same counts, the written types of the arguments decide as far as "C# argument types beside an instance method" below says; where they say nothing, the instance method is taken. A reading whose condition holds binds nothing: `classify` answers `absent` for it, exactly as for a name the repository does not declare, and `resolve` and `resolveFile` answer nothing, so the group ends in silence and a consumer that counts `ambiguous` answers counts none for it. A receiver whose type the file does not write (`var`, a call result, an inferred lambda parameter) carries no condition. In a `CsharpExtract`, an extension call (an `ext` descriptor) names its receiver's written types by their places in the new top-level list `receiverTypes` (its field `on`), and the types around it by a place in the new top-level list `lists` (its field `from`), so calls on one declaration and calls in one type body share them; a call with no receiver type to ask is written as before, with none of this. The two lists are part of the extract as `refs` is: an extract holds each of them whenever one of its `refs` names a place in it, and leaves it out only when none does. A consumer that stores the extract stores `lists` and `receiverTypes` with `refs`; an extract stored by an earlier build is stale by the C# extractor's `rev`. Where a descriptor names a place the extract does not hold, `assembleCsharpCandidates` gives no candidate group for that call: it gives no edge, and nothing throws. The C# extractor's `rev` says so.

**C# extension methods by the call's counts (added in 1.1.0).** A call binds an extension method only when the method can take its arguments. A file's `declarations()` now record, under each extension key it declares (`<ns>.<Name>()` and `<ns>.<Class>#<Name>()`), the shapes of its extension methods of that key: `shapes:<key>`, a tab, and one entry per method joined by spaces, `<type parameters>:<required parameters>:<all parameters>` without the receiver (the last `*` for a `params` list; the first `*` for a member of a C# 14 extension block, whose block may hold type parameters of its own), led by `-` for a method only its own assembly sees. Every reading of an extension call's candidate group carries the optional field `takes` (on the `symbol` form of `TargetHint`), the number of the call's arguments beside the receiver and of its written type arguments. Where such a reading would bind one owner, `makeResolver` asks whether that owner declares a shape that takes those counts, reading every `shapes:` record of the reading's keys whose file is a bound definer or belongs to the same owner as one, and each only as far as the calling file sees it: with `reach` given, a file of a project out of reach has no say, and neither has a method marked `-` for a caller of another compilation that is no friend, exactly as a definer out of reach is dropped before the owners are counted; when no shape left takes the counts, the reading binds nothing (`classify` answers `absent`, `resolve` and `resolveFile` nothing), and the walk goes on to the next reading, as C# goes on to the next enclosing namespace. So `sessions.FirstOrDefault(s => s.Active)` gives no edge to a `FirstOrDefault<T>(this IReadOnlyList<T>)` of the repository that takes no argument. A reading that names two owners stays `ambiguous` whatever their shapes when the call's receiver type is not written: the counts choose no one among several, and a consumer's count of `ambiguous` answers does not move for such readings. Where the receiver's type is written, the next paragraph narrows the owners first, and a reading that was ambiguous can bind. The shapes are read from the records themselves and never through the files the table lists under the extension key, so a consumer that keeps only some files per name key (one per owner) gets the same answer as long as it hands the table every `shapes:` record of every file, as it does every other key with a tab. A bound definer whose `shapes` record the table does not hold takes any call, as before. In a `CsharpExtract`, an `ext` descriptor now writes `args` and `typeArgs` on every call where they are not zero; an extract stored by an earlier build is stale by the C# extractor's `rev`. A consumer's graph can lose extension-method edges it showed before, each one a call the method could not take. The C# extractor's `rev` says so.

**C# extension methods by the receiver's type (added in 1.1.0).** An extension call whose receiver's type the file writes (`Order o` and `o.Tag()`) can tell the extension methods of one name apart by the receiver they take. A file's `declarations()` ends the shape of each classic extension method in its `shapes:<key>` record with `|` and the written type of its first parameter, as a record writes a type (the keyword of a predefined type, `<offset>:<name>` for a named one; nothing for a type parameter, an array or a tuple, and nothing for the receiver of a C# 14 extension block), and `TargetHint` (the `symbol` form) gains the optional field `takes.receiver`, the ordered readings of the receiver's written type. Where a reading names more than one file and `takes.receiver` is given, `makeResolver` keeps the files with a method, as far as the calling file sees it, that takes the call's counts and whose receiver does not refuse a value of that type for certain (the type itself, a type it derives from or implements; a parameter whose type is not known to the repository, an alias or a type with an implicit conversion refuses nothing). When one file is left the reading binds it, when none is the reading binds nothing and the walk goes on to the next namespace, and when several are the reading stays ambiguous. A reading without `takes.receiver`, or whose receiver's type binds no one type of the repository, is unchanged. A method that is private to its static class is led by `~` in the record and counts for a call in its own file only. A consumer that stores a record stores it whole; a record stored by an earlier build is stale by the C# extractor's `rev`.

**C# argument types beside an instance method (added in 1.1.0).** An instance method takes a call only when each argument converts to its parameter's type. An entry of a `methods:<type key>` record now ends with the written types of the method's parameters where it writes one the record can hold: `GetItemById:0:1:1(12:Guid)`, `Save:0:2:2(string,40:Order)`. Each is the keyword of a predefined type, `<offset>:<name>` for a named type (as a base record writes one), or empty for any other parameter (an array, a tuple, a type parameter, a parameter with a modifier such as `ref` or `params`); a nullable type is written as the type under it, and trailing empty ones are left out. An enum also declares `enum:<type key>`, and a type that declares an implicit conversion operator `converts:<type key>`. On a call that carries a receiver type, the `instance-method` condition (and the `call` of `no-member`) gains the optional field `argTypes`, one `CsharpArgType` per argument: the keyword of a predefined type, `{ type }` with the readings of the written type of the parameter, field, property or local the argument is, `{ member }` with the readings of the type a member is read through (`ImageType.Primary`, the argument's type when that type is an enum), or null. An instance method that fits the call by its counts does not take it when a parameter cannot take its argument for certain: a predefined type takes only what the language's own conversions give (`object` takes everything); a type of the repository takes what derives from it or implements it, and nothing else unless it or the argument's type declares a conversion operator or the argument's type has a base outside the repository; a type outside the repository refuses only a predefined type or an enum value, and only where it is one of `Guid`, `DateTime`, `DateTimeOffset`, `TimeSpan`, `DateOnly`, `TimeOnly`, `CancellationToken` (for an enum value, anything but `Enum`, `ValueType`, `Object` and the interfaces `Enum` implements). Everything this reading does not know takes the argument, so the answer is the one of counts alone: an argument that is a literal, a `const` field or local (a constant converts by its value), a call result, a `var` local or a property of another value, a `dynamic` parameter, a named argument, an argument passed by `ref`, `out` or `in`, a `dynamic` one, and a parameter type that is an alias or that two imported namespaces declare. So `libraryManager.GetItemById(id)` with `string id` binds the extension `GetItemById(this ILibraryManager, string)` beside the instance `GetItemById(Guid)`. In a `CsharpExtract`, an `ext` descriptor that carries a receiver type gains `argTypes`: a keyword, a place in `receiverTypes`, `[place]` or `[place, list]` for a member read through a type (the second number the place in `lists` of the types around the call that can hold a member of that first name), or null; trailing nulls are left out, and the field when the file writes no argument type. A consumer's graph can show extension-method edges it lost to an instance method of the same counts. With the parameter types, the extension shapes and the two marks, the declared keys of jellyfin are about 1.4 MB (1.2 MB before them). The C# extractor's `rev` says so.

**C# members of the enclosing type (added in 1.1.0).** C# reads the members of the types around a simple name, inherited ones included and from every part of a partial type, before any namespace. `Settings.Get()` in a class that inherits a property `Settings`, or whose other part declares one, reads that property and no static class `Settings`. The C# extractor's `declarations()` now lists the members of a type that are no types (a field, a constant, a property, an event, a method, a record's primary constructor parameter): `members:<type key>`, a tab, and one entry per name joined by spaces, `<name>` or, for a field or a property whose written type is a named type, `<name>=<offset>:<type name>` in the form of a base record; a private member, and a primary constructor parameter of a class or a struct, is led by `-`. Only a type whose members other code can read by a simple name lists them: a `partial` type, an interface, and a class or a record that is neither static nor sealed; a private member is listed only in a `partial` type. A field or a property named as its own type (`public SourceType SourceType { get; }`) is not listed, because C# reads that name as the type wherever a type fits, so `SourceType.Library` keeps its edge. Inside a type that is `partial` or lists a base, every reading of a receiver's candidate group carries the condition `member` in its `unless` list (`CsharpCondition`): it holds, and the readings bind nothing, when the nearest type around the receiver that knows its first name has it as such a member, declared in any part or inherited from a base class in the repository. A private member of a base class is not seen there, a nested type found nearer still binds, and a type position (`Color _c;`) ignores members as the language does. An explicit interface implementation (`ISettings IHasSettings.Settings => …`) is no member of its class by that name, in the record and in the file that writes it: `Settings.Get()` beside it names the type `Settings`. Inside such a type, an extension call whose receiver's first name the file does not declare now gives a candidate group too, each reading under the condition `no-member`: the readings are read only when the name is such a member, and where the receiver is that member alone and its written type has an instance method the call fits, they are not. A call on `this.<name>`, where the file declares no member of that name, is read the same way: the name is a member of the type around the call, declared in another part or inherited, so its `ext` descriptor carries `member` with `own: true` and the one type around it, and the `no-member` condition carries `own`: it holds only where that member's written type has an instance method the call fits, and where no type of the repository declares the member the readings stand. So `this._config.Get(key)` and `_config.Get(key)` answer alike when another part declares `_config`. Inside a type that is neither `partial` nor lists a base nothing changes. In a `CsharpExtract`, a `receiver` descriptor names the types that can hold such a member by a place in the top-level list `lists` (its field `members`), and so does such an extension call (`member.types` of its `ext` descriptor). The list is stored with `refs`, as for an extension call's `from`: a receiver or a call that names a place the extract does not hold gives no candidate group, so no edge, and nothing throws. A reading whose condition holds answers `absent` from `classify`, never `ambiguous`. A consumer's graph can show new extension-method edges for calls on inherited members. A member inherited from a base class outside the repository (ASP.NET Core's `ControllerBase.User`) is a known limit: the repository holds no declaration to read, so a same-named type of the repository still gets the edge. The C# extractor's `rev` says so. From 1.2.0 a simple name in a pattern that C# binds as an expression first (`case Order:`, the switch arm `Order =>`, a subpattern of a positional pattern `(Order, _)`, `not Order`), and that the file does not declare as a value, is read the same way inside such a type: every reading of its candidate group carries the condition `member`, so `case Order:` in a class whose base class of the repository declares a constant `Order` reads that constant and gives no edge to a type `Order` a using imports, where it gave one before; where no part or base declares the name the edge stays. The is-type operator `x is Order` looks the name up as a type first and keeps its edge. In a `CsharpExtract`, such a name's `plain` descriptor names the types by a place in `lists`, in its new optional field `members`, which a `plain` descriptor of any other reference never carries; as for a receiver, a place the extract does not hold gives no candidate group. A consumer's graph can lose such edges. The C# extractor's `rev` says so.

**C# dotted receivers, step by step (added in 1.1.0).** C# binds the first name of `Data.Row.Parse()` at the nearest place that knows it, a type around the call, then each enclosing namespace from the innermost outward, each followed by what its using directives import, and reads the next name in what it found. The candidate group of a dotted receiver (and of a dotted name in a pattern, `o is Data.Row`) is now ordered that way: at each step every prefix of the receiver, shortest first, before any reading of a step farther out. In `namespace App.Web`, beside a namespace `App.Data` that declares `Row` and a class `Data` of the global namespace, the receiver names `App.Data.Row`; before, every reading of `Data` came before any of `Data.Row`, and the global class took the edge. A dotted name in a pattern is read once, as the whole name. The readings are the same set as before for a receiver of one name. Where the nearer namespace exists and holds no such type, the farther readings are still read: the extractor does not know whether the calling project sees that namespace. The C# extractor's `rev` says so.

**Rust crate-root items (added in 1.1.0).** `use crate::Error;` names what the crate-root file binds as `Error`, and so does `use core_lib::Error;` in the root file of the path dependency `core_lib`; in an edition 2015 crate a `use` path is relative to the crate root, so `use Error;` names an item the crate-root file binds at its top level. Which names those are is read from the root file's parse tree, never from its text: the Rust extractor's `declarations()` now also declares, for every file, each name its top level binds as an item (an item it defines, the derive a function with `#[proc_macro_derive(Name, …)]` defines, beside that function's own name, also where a `cfg_attr` applies the attribute (`#[cfg_attr(feature = "x", proc_macro_derive(Name))]`), an item of an `extern` block, a name a top-level `use` brings in, and the items of `thread_local!`, `lazy_static!`, `bitflags!` and `cfg_if!`) under the key `item:<name>`, and each name its top level binds with `extern crate` (the alias, else the crate), also in a branch of a `cfg_if!` among its items, under the key `extern:<name>`, beside the keys it gave before, and the Rust extractor's `rev` says so. A name bound with `extern crate` is one a `crate::` path or a path into a dependency goes through (`pub extern crate inner as name;` in a facade), and no item an edition 2015 `use` path names. Which crate such a name stands for is declared under `extern:<name>=<crate>`: `extern crate a as b;` in a crate root makes `b` name the crate `a` in every module of that crate, in every edition, and when `a` is an in-repo path dependency, `use b::X;` binds its library. Written anywhere else, the declaration binds `b` in its own module or block only, and the extractor's `uses()` says so in the path it emits: the declaration itself is emitted as `extern::a`, a crate named for certain, and a `use` that starts with `b` as `extern::a::as::b::X` where it stands in that scope or in a function body or a block inside it, unless a nearer block binds `b` itself (a `use`, a `mod` or another item of the type namespace; an inline module is another module, where `b` is not bound), which is the crate from edition 2018 on and the path as written in edition 2015. A `self::` or `super::` path whose next name the file of the module it reaches binds at its top level with `extern crate` (`extern crate util as u;` in `src/net/mod.rs`, then `use self::u::Marker;` there or `use super::u::Marker;` in its child) names that crate in every edition, read from that file's `extern:` keys in the table; where two roots certainly compile the file, a path that climbs to the crate root reads none. `extern` is a keyword, so no path of the source starts with it. In edition 2015 a `use` path cannot start with a crate the root does not bind, the package's own library included: its first segment is what the first crate root that binds it makes of it, a crate bound there with `extern crate` or a module or an item of that root. So `use app::Engine;` in a binary of the package `app` names the library only where that binary's root writes `extern crate app;`, and names the root's `mod app;` where it declares one. So `use util::slug;` names the root's `mod util;` where the package also has a path dependency `util`, and names nothing where the root has neither that module nor `extern crate util;`; the `extern crate util;` line itself binds the dependency wherever it stands.

`makeResolver` passes its `SymbolTable` to `resolvePathToFile` as an optional fifth argument (`ResolverDeps.resolvePathToFile` takes it), and the function `makeResolvePathToFile` returns reads that table for these questions and for the module declarations described next. It reads a crate root from the table alone and never from the root's text, so **the table must hold every key the extractor declares for every crate-root file**, each under that file: a table that keeps only some of the files of a key, or that leaves a root file out, loses the edges that go through that root. `use core_lib::Engine;` against a root's `pub use engine::Engine;` then gives no edge, and in an edition 2015 crate whose root file is not in the table every import of a path dependency gives none, because the `extern crate` that would bind it is not seen. A consumer that builds its table from every file's declarations and hands `makeResolvePathToFile`'s function to `makeResolver` needs no change; a consumer that compacts or filters its table must keep the keys of the crate roots whole. Called without any table, the function has no parse tree at all and answers as 1.0 did: it binds a root file for a `crate::` path or a path into a dependency when the file's text declares the name anywhere, which a word in a string or an item nested in a function also satisfies; it resolves a path dependency in edition 2015 as it does from 2018 on; and it knows no item of a root and no name bound with `extern crate`, so an edition 2015 `use` path of a root's own module and a path through an alias written in another file stay silent (an alias used in the scope that writes it binds without the table). A name the root defines only inside an inline `mod`, a function body, an initializer, a closure or a `macro_rules!` body, or through a macro whose expansion is not known, gives no edge; a root file the pass did not extract gives none either.

**Rust glob re-exports of a crate root (added in 1.1.0).** A crate root that writes `mod types; pub use types::*;` re-exports every public item of `types` without naming one. `use kit::Order;` against such a root, and `use crate::Order;` inside the crate, now bind the root file, as a named re-export of the item does; across a path dependency this can be the only edge between the two crates. The Rust extractor's `declarations()` declares the path of each top-level glob `use` of a file under `glob:<path>`, as written and without the `::*` (`glob:types`, `glob:self::types`, `glob:crate::a::b`; a group gives one key per glob in it, and a path that starts with `::` gives none), and the Rust extractor's `rev` says so. The function `makeResolvePathToFile` returns binds the root for a name the root does not write when exactly one module that a glob of the root names declares the name at its own top level (its `item:<name>` key): the module is a file of the root's own tree, named by its path from the root, bare or after `self` or `crate`. A name two globs of the root both bring in gives no edge, as Rust refuses it where it is used, and so does a name the glob's module does not declare. A glob that a `cfg` in front of its `use` may remove (`#[cfg(unix)] pub use unix::*;`, or a `cfg_attr` there that applies a `cfg`) is declared under `glob?:<path>` as well, beside its `glob:<path>`, and the Rust extractor's `rev` says so: where a `cfg` may remove all but one of the globs that bring a name in (`#[cfg(unix)] pub use unix::*;` beside `#[cfg(windows)] pub use windows::*;`), at most one is there on any one target, and the name binds the root. `glob?:<path>`, like `glob:<path>` and every other per-file key of these paragraphs, is a key a consumer keeps whole: the word before its one `:` is lowercase and is no Rust path, so the key is never split at `::`, shortened or merged with another. A glob of a module that itself re-exports through a glob, and a glob of another crate (`pub use inner::*;` in a facade), are not followed. The table must therefore hold the `item:` keys of the modules a root's globs name, each under its file, beside every key of the root, its `glob?:` keys included: a table that drops them takes every glob for one nothing can switch off. A consumer's graph can show new edges to crate roots.

**Rust names in scope (added in 1.1.0).** From edition 2018 a `use` path may start with a name in scope of the module that writes it, and Rust finds such a name before a crate of the same name. `mod shapes; pub use shapes::Circle;` names the module the file declares, and `use crate::shapes; use shapes::round::Arc;` goes on from the name the first `use` bound, which can be the only edge to the file it ends in. The Rust extractor's `uses()` says so in the path it emits: `use::<n>::<the n segments the name stands for>::<the path as written>`, so `use::2::self::shapes::shapes::Circle` for the first and `use::2::crate::shapes::shapes::round::Arc` for the second. `use` is a keyword, so no path of the source starts with it, and the Rust extractor's `rev` says so. The names read are the modules a module declares, with or without a body, and the names the `use` declarations in scope bind (a path's last segment, a group's members, an alias, a `self` member; never a glob), followed through one another; the scopes are the blocks around the `use`, outward, and the module around them, never an outer module. Two `use` declarations that bind the name to different paths (one under each `cfg`) leave the path as written. In edition 2015 a `use` path starts at the crate root whatever is in scope, so the function `makeResolvePathToFile` returns reads the path as written there. A consumer that stores hints stores the new form; one stored by an earlier build is stale by the `rev`. A `use` path that starts with `::` (`use ::shapes::Circle;`) gave no hint before and is now emitted without the `::`, and never as a name in scope: in edition 2015 it starts at the crate root, so it binds the root's module `shapes`, and from edition 2018 on it names a crate only, so it binds a path dependency `shapes` and never a module of the crate. A file-backed `mod x;` inside a branch of `cfg_if!` gave no hint before, because the macro's body is tokens to the grammar. The Rust extractor's `uses()` now emits it as it emits one written outside the macro, from the line of its `mod`: every branch, a `cfg_if!` nested in a branch, and a `mod` inside an inline `mod y { … }` written there (`self::y::x`); a `mod` with a `path` attribute is skipped as elsewhere. Only a `cfg_if!` among the items of a module is read, not one in a function body. A consumer's graph can show new edges from a platform layer to its modules.

**Rust module declarations (added in 1.1.0).** A package can have several crate roots over one directory: `src/lib.rs` beside `src/main.rs`, a `[[bin]]` whose path lies in `src/`, or the binaries of `src/bin/` above a directory without a `main.rs`. Which of them compiles a module file is read from parse trees: the Rust extractor's `declarations()` now also declares, for every file, each module the file places in a file of its own by name alone. The key is `modfile:<path>` for a declaration nothing can switch off, and `modfile?:<path>` for one that a `cfg` may remove: a `cfg` on the `mod`, on an inline module around it, or at the head of that inline module or of the file. A `cfg_attr` at such a head counts when it applies a `cfg`, read from its tokens, so a comment inside it changes nothing and a `cfg` written inside another attribute (`doc(cfg(…))`) applies none; a `cfg_attr` there whose tokens do not read as a predicate followed by attributes may apply a `path`, so the file then declares no module by name alone and its `mods:all` is not declared. The path is the module's names from the declaring file's own module, joined by `/`: `modfile:x` for `mod x;`, `modfile:outer/x` for one inside the inline module `outer`. The Rust extractor's `rev` says so. Only a plain `mod x;` is declared: none with a `path` attribute, a `cfg_attr` or an attribute macro in front of it or around it, none inside a function body or a macro, and none from a file that does not parse to the end. The function `makeResolvePathToFile` returns follows these declarations from a file up to the roots, through the same table `makeResolver` passes. A root reached by `modfile:` declarations alone certainly compiles the file; a root reached through a `modfile?:` declaration compiles it in some configuration at most, and whether its `cfg` ever holds is not read. `crate::Item` binds the first root that holds the name, in this order: the root that certainly compiles the file, then the roots that may compile it under a `cfg`, then the other roots in the order they had in 1.0.0, the library first. Two or more roots that certainly compile the file give no edge for a root item; a root under a `cfg` is never one of the two. A root not reached is not ruled out, because a `path` attribute, `include!` or a macro can place a file anywhere. The edition of a file follows the same roots: an edition 2015 `use` path names an item of the roots reached when they are all edition 2015, or of the library and `src/main.rs` when those are, and never an item of a root with another edition. Called without the table, the function knows no declaration and keeps the order of 1.0.0 for every file; a file in a directory of `src/bin/` without a `main.rs` then has no known crate, and its `crate::` paths give no edge. A consumer that builds its table from every file's declarations needs no change.

**Rust declared modules (added in 1.1.0).** A file is a module only when a `mod` item declares it. `use crate::util::parse;` names the function `parse` of `src/util/mod.rs` where that file declares no `mod parse;`, whatever lies at `src/util/parse.rs`, and `crate::serve()` written in the binary `src/bin/server.rs` names its own function, never the other binary `src/bin/serve.rs`. The Rust extractor's `declarations()` now declares, for every file, each module the file declares without a body under `mod:<path>`, the path being the module's names from the declaring file's own module joined by `/` (`mod:x`, `mod:outer/x`), whatever stands in front of the `mod` and also in a `cfg_if!` branch; and the key `mods:all` when those are all of them, which is so unless the file does not parse to the end, has an inner attribute at its head that is not one of the compiler's, or invokes among its items a macro other than `cfg_if!`, `thread_local!`, `lazy_static!` and `bitflags!`, since a macro can expand to a `mod`. The Rust extractor's `rev` says so. The function `makeResolvePathToFile` returns binds a file whose name fits a path as a module when a file of a module above it declares it. Where every such file that exists carries `mods:all` and none declares it, the name is an item of the module above, and that module's file is bound; an inline module of that name (`mod codec { … }` beside a leftover `codec.rs`) is such an item. Where that is not known for one of them, the fitting file is bound as before, unless it is the root file of a Cargo target, which is a crate of its own. The table must therefore hold a file's `mod:` keys whenever it holds its `mods:all`: a table that keeps `mods:all` and drops a `mod:` key turns that module's file into a file no path binds. Called without the table, the function knows no file's modules and binds every fitting file, as 1.0 did. A consumer's graph can show edges that move from a leftover file to the module that defines the name.

**Rust files loaded through a path attribute (added in 1.1.0).** Rust treats a file that a `#[path]` attribute on a `mod` outside inline modules loads as a mod-rs file, whatever its name: the `mod epoll;` of `src/platform/linux.rs`, loaded by `#[path = "platform/linux.rs"] mod sys;`, is `src/platform/epoll.rs` or `src/platform/epoll/mod.rs`, beside it, and no file under `src/platform/linux/`. The Rust extractor's `declarations()` declares each such file under `pathmod:<path>`, the attribute's path normalized and relative to the declaring file's directory (`pathmod:platform/linux.rs`, `pathmod:../shared/util.rs`), and under `pathmod-name:<file name>` (`pathmod-name:linux.rs`), by which the function `makeResolvePathToFile` returns finds the files that may load a given file; the Rust extractor's `rev` says so. A `mod` and a `self::` path written in a file loaded that way then resolve beside it, and where nothing beside it fits, under the directory named after it as before, since the same file can also be a module by its name. From 1.2.0 the `mod` that carries the attribute gives a use of that file, as the next paragraph says. A `super::` path of the loaded file starts from the module of the file that loads it, wherever the two lie: `super::Config` in `src/platform/linux.rs` names the `Config` of `src/lib.rs`, never of `src/platform/mod.rs`; where two files load it, its parent cannot be told and such a path names nothing. A file that the module above its place also declares by its name (`mod util;` in `src/lib.rs` for `src/util.rs`, which `tests/it.rs` loads through `#[path = "../src/util.rs"]`) keeps that module as its parent, read first as before; the file that loads it is read only where that names nothing. Not read: a `path` attribute on a `mod` inside an inline module, in a `cfg_attr` or in a macro's tokens, and an absolute path. The table must hold both keys of the declaring file. A file declared by its name alone keeps its children under the directory named after it. A consumer's graph can show new edges from such a file to its modules.

**Rust modules moved by a path attribute (added in 1.2.0).** A file-backed `mod` with a `#[path]` attribute among the items of its file, outside every inline module, now gives a use of the file the attribute names. The Rust extractor's `uses()` emits it from the line of the `mod` as `mod::<path>`, the attribute's path normalized and relative to the directory of the file that writes it, as Rust reads it there whatever kind of file that is (`mod::../data/orphan.rs` for `#[path = "../data/orphan.rs"] pub mod via_attr;` in `src/ui/mod.rs`, `mod::data/d.rs` for `#[path = "./data//d.rs"] mod dd;`), and the Rust extractor's `rev` says so. `mod` is a keyword, so no path of the source starts with it. The function `makeResolvePathToFile` returns binds that file when it exists in a Cargo package; where it does not, `classifyUse` answers `absent` with the reason `unfollowed`. A `mod` inside an inline module, one under an inline module that carries a `path` attribute itself, one in a function body, one in a `cfg_if!` branch, one whose `path` a `cfg_attr` applies, and an absolute path still give no use. A consumer that stores hints stores the new form; one stored by an earlier build is stale by the `rev`. A consumer's graph can show new edges from a file to the modules it moves with a path attribute.

**Rust paths into a crate written outside a `use` (added in 1.2.0).** A path written in code, in an expression or a type, whose first name is lowercase and bound by nothing in scope where it stands names a crate of the extern prelude in every edition: `datacrate::dc()` in a function body, with `datacrate = { path = "datacrate" }` in Cargo.toml and no `use`, calls into that crate. The Rust extractor's `uses()` now emits such a path as `in::<the path as written>` (`in::datacrate::dc`), and the Rust extractor's `rev` says so; before, a path written outside a `use` gave a use only when it started at `crate`, `self` or `super`. `in` is a keyword, so no path of the source starts with it. The names read are those of the names-in-scope paragraph above, the modules a module declares and the names its `use` declarations bind, together with the structs, enums, unions, traits, type aliases and modules and the `extern crate` names of the blocks around the path and of its module; a glob `use` there may bring in any name, so a path under one gives no use, and neither does a path that starts with `::`, a capitalised name, `Self`, or a primitive type (`u32::MAX`), or the path of a tool's attribute (`#[rustfmt::skip]`). So a module the file declares hides a crate of its name: `mod datacrate;` beside `datacrate::local()` gives no use, while the same call in another module, where that module is not in scope, gives one. The function `makeResolvePathToFile` returns reads `in::` as a `use` path is read from edition 2018 on, in every edition and never from the crate root: a crate a crate root binds with `extern crate`, the package's own library, or a path dependency binds its library; `std`, `core` and a registry or git dependency bind nothing, and `classifyUse` answers `absent` with the reason `outside` for them. A consumer that counts the uses that leave the repository sees one for each such path, every `std::` call included. A consumer that stores hints stores the new form; one stored by an earlier build is stale by the `rev`. A consumer's graph can show new edges from code that calls a path dependency through its name.

**Single-file components (added in 1.2.0).** `sfcScriptView` reads the `<script>` elements of a Vue or Svelte component in document order and skips an HTML comment whole: a script inside `<!-- … -->` is no script, so a component whose only script is commented out has no view, and a script beside a commented-out one is read alone. A `<!--` starts a comment only in markup text: inside an attribute value, a raw-text element (`style`, `textarea`, `title` and the others an HTML tokenizer reads as raw text), a Svelte `{…}` expression or a script body it is text. A `<!--` with no `-->` after it is text too. A script element with a `src` attribute and no body gives a use of the file it names when the `src` is a relative path that starts with `./` or `../` and holds no quote or backslash, at the line of the element (`<script src="../data/d.ts"></script>`). Any other `src` gives no use, and so does a tag that runs over lines where the import does not fit on the line the tag starts on.

**Limits of the component reader (added in 1.2.0).** The reader follows an HTML tokenizer for a component's markup and does not parse Vue or Svelte. In a Vue template, `{{ … }}` is markup text here, so a `<!--` inside an interpolation starts a comment: when a `-->` follows, the scripts between them are no script, and a component whose only script lies there has no view (`{{ '<!--' }}`, then a script, then a `-->`). In a Svelte expression the braces and the JavaScript strings are counted, but a regular expression literal is not parsed: a brace in one can end the expression early, so a `<!--` after that point starts a comment that the next `-->` closes, and the scripts between them are no script; a quote in one can open a string that never ends, so the expression never ends and a commented-out script after it is read.

**TypeScript and JavaScript call forms (added in 1.1.0).** A `require('x')` call, an `import x = require('x')` and a dynamic `import('x')` read the `require` or `import` condition of a package's `exports` and `imports` by their own form, as TypeScript resolves them, where an `import` or `export` statement and an import type (`typeof import('x')`, `import('x').T`) read the condition of their file's format. A dynamic `import('x')` reads `import` except where the compiler emits it as a `require`: under a `module` that is neither a Node one nor `preserve`, in a file emitted as CommonJS (a `.cts` or `.cjs` file, and any other file under `module` commonjs, amd, umd, system or none), it reads `require`. An import type is told from a call by where it stands. The extractor reads the type nodes of the grammar (an annotation, a type argument, a type predicate, `typeof`, a union, a conditional or `readonly` type, the right side of `as`, `satisfies` and a type alias), and the places the grammar parses as expressions instead, which it recognises by their shape: the type argument of a class heritage clause, a call, a tagged template or a `new` (`Base<import('x').T>`), `keyof import('x').T`, a parenthesized type, and a template literal type. The heritage clause of an interface (`extends`) and a class's `implements` clause hold expressions to the compiler too, so an `import('x')` there is a dynamic import call, as the compiler resolves it. Known limits: `export interface I extends import('x').T {}` gives no edge, because the grammar's recovery from it loses the specifier; and a type spelling the grammar cannot read that is not in the list above keeps the call form of a dynamic `import()`, as does one that follows another the grammar cannot read in the same run of statements, since its recovery can run on into the next statement. The TypeScript extractor's `uses()` therefore marks those three forms: the `path` form of `TargetHint` gains the optional field `callForm`, `'require'` or `'import'`, absent on every statement that names no mode itself. The `resolution-mode` import attribute names one: a type-only import or re-export (`import type { T } from 'x' with { 'resolution-mode': 'import' }`, `export type { T } from 'x' with { … }`) and an import type (`import('x', { with: { 'resolution-mode': 'import' } }).T`) read the condition the attribute names, whatever the format of their file, as the compiler reads them. Their hint carries `callForm` `'require'` when the attribute says `require`, and the third value `'esm'` when it says `import`: the `import` condition under every setting, where `'import'` is a dynamic `import()` the compiler may emit as a `require`. The attribute on a value import, on an import with an inline `type` specifier or in the options of a dynamic `import()` decides nothing, as in the compiler. `ResolverDeps.resolvePathToFile` takes the hint's `callForm` as an optional sixth argument, and the function `makeResolvePathToFile` returns reads it for TypeScript and JavaScript files only. A consumer that builds its pass from the extractor's hints and hands `makeResolvePathToFile`'s function to `makeResolver`, as both consumers named in the table do, needs no change; a consumer that stores hints stores the field, and one stored by an earlier build is stale by the TypeScript extractor's `rev`. A file no tsconfig covers is read with the conditions Node and TypeScript enter by default, and a `types@<range>` key is entered when TypeScript 7.0.2 satisfies the range. That is the version Runes models for every project, whatever TypeScript the project itself uses: `types@>=7` and `types@7.0.2` are entered and `types@<7` is passed over, as TypeScript 7.0.2 reads them (1.0.x modelled TypeScript 6.0.3). A tsconfig that extends a preset Runes cannot read (a package that is installed and not in the repository, as every package is when the consumer excludes `node_modules` or resolves through a `FileView` of the commit) inherits a `module`, a `moduleResolution` and `customConditions` that are unknown wherever the config and its readable bases do not set them. The unknown ones are taken to be values the compiler accepts beside the known ones: a Node `module` goes only with a Node resolution, and Bundler only with `commonjs`, an ES kind from `es2015` on or `preserve`. The lookup is read once for each pairing that remains, and with a non-standard key both entered and passed over; it binds the file all of those readings name, and where they differ the first listed target that one of them names. So a `require()` call, an `import x = require()`, a `.mts` or `.mjs` file, an import outside an `import()` in a `.cts` or `.cjs` file, and any file of a config that sets a Node resolution or a `module` of `commonjs`, an ES kind or `preserve` itself bind as the compiler binds them with the preset installed, as long as no non-standard key (`browser`, `react-server` or a custom one) is listed before the branch. An `import()` in a `.cts` or `.cjs` file of a config that sets neither, and a config whose own `module` is `amd`, `umd`, `system` or `none`, fall back to the first listed target.

**Test mocks and unread bundler forms (added in 1.2.0).** `vi.mock('x')` (Vitest) and `jest.mock('x')` give a use of the file their first argument names when that argument is a string literal, or a template literal with no substitution, read as a dynamic `import('x')` is: the `import` condition, and the same edge. Any other first argument gives none. `import.meta.glob(…)` (Vite) and `require.context(…)` (webpack) are unread: they give no use, so a file reached only through them has no edge.

**Python source roots from configuration (added in 1.2.0).** Every directory that holds a `pyproject.toml`, `setup.cfg` or `setup.py` is a Python project, and its source roots are what an installed project puts on `sys.path`. They are the directories its configuration names, read from these keys only: in `pyproject.toml`, `[tool.setuptools.packages.find] where` (an array of strings), the empty key of `[tool.setuptools] package-dir` (`package-dir = { "" = "lib" }`, or the table `[tool.setuptools.package-dir]`), the `from` of each element of Poetry's `[tool.poetry] packages` (an element without `from` names the project's directory), the directory of each path of Hatch's `[tool.hatch.build.targets.wheel] packages` (`lib/pkg` names `lib`), maturin's `[tool.maturin] python-source` and the PDM backend's `[tool.pdm.build] package-dir` (each a string; a mixed Rust and Python project with `python-source = "python"` has its package's absolute imports resolve under `python/`), and Hatch's `sources` under `[tool.hatch.build.targets.wheel]`, or under `[tool.hatch.build]` when the wheel target sets none (the target's option replaces the build-wide one, as hatchling reads it, also when it is empty or refused), as an array of strings (`sources = ["lib"]`, each a prefix the wheel drops) or a mapping, inline or as its own table, whose every member maps a prefix to `""` (`"lib" = ""`); in `setup.cfg`, the empty key of `[options] package_dir` (`package_dir =` then `= lib`) and the first directory of `[options.packages.find] where`. A key is found by its full key path, so a dotted key under a parent table reads alike. When the configuration names none of them, or none that is a directory of the repository, the roots are as in 1.1.x: the project's `src/` child when it exists, else the project's directory. A named root replaces that rule, as `src/` replaces the project's directory, so a package in `lib/` named by `where = ["lib"]` has its absolute imports (`from pkg.data import x` in `lib/pkg/ui/a.py`, and from the tests beside `lib/`) resolve under `lib/`, where 1.1.x answered them `outside`. Any other key or form names no root (an inline `packages = { find = … }`, Poetry's `[[tool.poetry.packages]]` and a `packages` with an element that installs under another name with `to`, a mapping of a named package such as `{ "pkg" = "lib/pkg" }`, a Hatch `sources` mapping with a member that rewrites a prefix to another (`"lib/pkg" = "other"`), a parent table written inline (`build = { package-dir = "lib" }` under `[tool.pdm]`), a `setup.cfg` key written in another case, which setuptools does not read as the key, `setup.py`), nor does a key whose value cannot be read whole (an element that is not a string), a path that is absolute, holds a backslash or climbs out of the project's directory, or a key `setup.cfg` writes twice. A root read from configuration is one of the discovered roots: a top-level name the standard library owns is never matched there, and a module two roots hold binds no file. A project whose directory is, or lies below, a directory named `tests`, `test` or `fixtures` is a test fixture, which nothing installs: from 1.2.0 its roots serve only the files inside its directory, so a module it holds no longer captures an import elsewhere in the repository (`import build` in the project's own code is the installed `build` package and answers `outside`, where 1.1.x bound a fixture's `build.py`, or answered `unfollowed` when several fixtures held one). The rule goes by the directory's name alone: a real project of the repository kept under a directory named `tests`, `test` or `fixtures` (a workspace member at `test/`) is taken for a fixture too, so its modules answer `outside` from the rest of the repository. A file in a package directory below a project's `src/` child or a root its configuration names is imported through that root and not run as a script, so from 1.2.0 its own directory is not searched as a root unless pytest or Django runs from it: `poetry.json` in `src/poetry/factory.py` resolves to the `poetry` package, where 1.1.x answered it `unfollowed` because `src/poetry/poetry.py` beside it competed (in `src/poetry/poetry.py` itself, with the importing file). Below a flat project's own directory, where script folders sit beside the packages, the importing file's directory stays a root. From 1.2.0 whether a directory above the importing file is a root is judged against each project's directory as well as its source roots: a directory strictly below a project's directory or one of its roots, and neither a project's directory nor a root itself, is no root unless pytest or Django runs from it. So beside `src/` or a configured root, `import util` in `scripts/sub/run.py` no longer binds `scripts/util.py`, which Python, running the script with `scripts/sub/` on `sys.path`, would not load; and below a root manifest a member's `tests` package keeps `tests.helpers` (pytest inserts the member's directory), which 1.1.x answered `outside`. Two directories stay roots whatever the layout, as running the file puts them on `sys.path`: for a pytest test module (`test_*.py`, `*_test.py`) or a `conftest.py`, pytest's basedir, the first directory upward without `__init__.py` (`tests/` for `tests/unit/test_a.py` when `tests/unit/` is a package and `tests/` is not, also below a flat project, and the test module's own directory in a namespace directory below `src/`); and for an import whose first name is the importing file's own top-most regular package (`myext.util` inside `docs/_ext/myext/`), the directory above that package, unless it lies below a source root. A directory only other code puts on `sys.path` (a test fixture's `sys.path` insertion) stays unseen. Two kinds of answer move with it: a top-level name only a directory inside a project holds answers `outside` (`import celery` in flask's `examples/celery/src/`, which 1.1.x answered `unfollowed` because `examples/` held the example's `celery` directory), and one a project's own directory holds answers `unfollowed` (`docs.*` in airflow's `airflow-core/docs/conf.py`, held by `airflow-core/docs/`, which 1.1.x answered `outside`). The readers take the manifests' lines as they find them and report no diagnostic.

**Go `replace` directives (added in 1.2.0).** A Go import binds through the modules the importing file reaches: its own `go.mod`, every `go.mod` above it, the members of the nearest `go.work`, and from 1.2.0 the modules its own `go.mod` replaces with a directory of the repository. A `replace <module> => <dir>`, with or without a version on the left and in the single-line or block form, is taken when `<dir>` begins with `./` or `../`, stays inside the repository and holds a `go.mod` that declares `<module>`, which the toolchain requires of a directory replacement; one whose left side names a version (`replace example.com/data v1.0.0 => ../data`) replaces only that version, so it is taken only when the `go.mod` requires the module at that version. So a repository whose modules are wired by `replace` and no `go.work` (`ui/go.mod` writing `replace example.com/data => ../data`) has `import "example.com/data"` in `ui` resolve to the package files in `data/`, where 1.1.x answered it `outside`. A replacement by another module and version, by an absolute directory or one outside the repository, by a directory with no `go.mod` or whose `go.mod` declares another module, and a `replace` in the `go.mod` of another module than the importing file's, are not taken: the import stays as it was.

**What a use comes to (added in 1.1.0).** `TargetResolver` gains the optional method `classifyUse(candidates, fromFile, language)`, which `makeResolver` always provides (its return type says so; a resolver written by hand may leave the method out). It walks one use's candidate group exactly as `resolveDetectedEdges` walks it: it answers `resolved` exactly where the walk makes an edge, with the same owner and file, and a nearer `ambiguous` ends the use as it ends the walk. `classify`, `resolve`, `resolveFile` and the edges answer as before. The answer is a `Classification` that carries what `classify` leaves out. The `ambiguous` form gains the optional field `candidates`, which `classify` never sets: the files the use could name, sorted and without repeats. Those are the files declaring the name in each owner (a C# partial type, a JVM name two modules declare, a Ruby constant), every file declaring into the package a Java or Kotlin star import names, a file whose declarations could not be read and may hold the name, and for Ruby the files of the namespace its lookup stops at or of a nested constant the reference may inherit. A Go import of a package of the module whose files belong to more than one owner, which `classify` answers `absent` and the edge walk passes by, is `ambiguous` with the package's files, unless a farther candidate of the use binds. From 1.2.0 the same holds for a Python import of a module that two or more source roots hold (two projects of the repository that each have a `shared/util.py`, whose order on `sys.path` the repository does not tell), and for a PHP class that two or more autoload directories map to files (two PSR-4 directories of one prefix, or the maps of two composer.json files): 1.1.x answered them `absent` with no candidates, `unfollowed` where the readers could place them.

The `absent` form gains the optional fields `reason` and `resolvedFile`, which `classify` never sets either. `reason` tells a use that leaves the repository from one the readers could not follow, in TypeScript, JavaScript, Python, Go, Rust, PHP, Java, Kotlin and C#; in C, C++ and Ruby it is left out. It is `outside` for an installed package, a Node built-in or a subpath of a package no workspace of the repository holds, a Python module whose top-level name no root of the repository holds (the standard library, an installed package), a Go import path no module of the repository holds, a Rust path that starts at a crate the repository does not hold (`std`, `core`, a registry dependency), a PHP class under no prefix of the repository's Composer maps, a Java or Kotlin name in a package the repository declares nothing in or below (`java.util`, `kotlinx.coroutines`, a sub-package nothing declares into), a simple Java or Kotlin name that the default imports hold (`String`, `kotlin.collections.List`) or that an on-demand import of such a package can give (`List` under `import java.util.*;`) and that no starred package of the repository declares, and a C# name only a namespace the repository does not declare can give (through a using of `System.Text`, an alias of a namespace from elsewhere, or written whole as `System.Console`). It is `unfollowed` for a relative path with no file, a `paths` alias, a path under `baseUrl` or a `#` import of the package, a package of the repository, a relative Python import that binds no file (from 1.2.0 a name imported from a relative module that is no module itself binds that module's file, as the absolute form does: `from ..data.m import x` binds `data/m.py` and `from ..data import x` binds `data/__init__.py`) or one under a top-level package the repository holds, an import path under the repository's `go.mod` module, a `crate::`, `self::` or `super::` path or one into the package's own crate or a path dependency, a class under the repository's PSR-4 or PSR-0 prefix, a Java, Kotlin or C# name that every reading places in the repository's own packages or namespaces (a simple name the repository does not declare, which no using of a namespace from elsewhere can give), a simple name a starred package of the repository declares, and a member of a type of the repository that the type's file does not declare (`Sub.Inner` inherited from a base class, a generated `Person.PersonBuilder`). It is `unowned`, with `resolvedFile`, when the use binds a file of the repository that no owner maps. The values of `reason` and of `explainMiss`'s answer are not closed: a later 1.x release may add one (C, C++ or Ruby may gain reasons; a finer value may split one of these), so a consumer reads a value it does not know as no reason, as it reads an absent answer without `reason`. The kinds of `Classification` stay the three they are. A use's readings decide in order: the first that leaves the repository, commits to a name of the repository, or binds an unmapped file gives the reason. A C#, Java or Kotlin name is read as the compiler looks it up: its first name at each level the reading gives (the enclosing namespaces and types, the package, a using), then each next name in what the one before named; Runes reads the readings the extractor writes and does not know which namespaces the referenced assemblies or libraries declare, so a name of the repository's namespace that some library also declares into reads as the repository's. A type an annotation processor generates into the file's own package (`AutoValue_Use`, `DaggerAppComponent`) has no file in the repository, so where a star import of a library could give its simple name, `classifyUse` answers `outside` for that use of generated code; without such a star import it answers `unfollowed`.

To tell these, `ResolverDeps.resolvePathToFile` may carry the method `explainMiss`, which the function `makeResolvePathToFile` returns does: asked with the same arguments about a path that bound no file, it answers `outside`, `unfollowed`, `{ split }` with the files, sorted, of a Go package split between owners, of a Python module several source roots hold or of a PHP class several autoload directories map (from 1.2.0), or undefined where it cannot say (C, C++, Ruby; a file of no Cargo package or Go module; a repository with no Composer map; a tsconfig it cannot read). A consumer that hands `makeResolvePathToFile`'s function to `makeResolver` reads these answers with no other change; one that wraps the function keeps its answers by passing `explainMiss` on.

**Stopping a parse (added in 1.2.0).** `parseFile` and `withParsedFile` take an optional last argument, a `ParseFileOptions` with one optional field, `progressCallback`. The language argument before it keeps its meaning (a string, or `undefined` or `null` for none); an object there is refused with a `TypeError`, so a JavaScript caller that puts the options in its place learns it at once. The runtime calls the callback as the parse proceeds, with the runtime's own `ParseState` (in web-tree-sitter 0.27, `currentOffset` and `hasError`). `currentOffset` counts the text as the runtime reads it, in UTF-16 bytes: two for each character of the JavaScript string, so a stop after `n` characters is `state.currentOffset > 2 * n`. When the callback returns `true`, the parse stops: the call rejects with an error whose `code` is `EPARSESTOPPED`, no tree is made, and `withParsedFile` never calls its function. A callback that throws stops the parse the same way, and the call rejects with what it threw. Either way the host resets its parser, so the next parse on the same host gives the whole tree of its own file. Without the argument no callback reaches the runtime and every parse runs as in 1.1.

**A runtime abort (changed in 1.2.0).** The runtime aborts on some texts, at its 2 GiB memory limit for one, and stays damaged for the rest of the process: a parser made afterwards can fail on any text. A parse the runtime aborts is not retried. The call rejects with an error whose `code` is `ERUNTIMEABORTED`, with the runtime's error as its `cause`, and from then on the host makes no call into the runtime: every later `parseFile`, `withParsedFile`, `getParser` (for a grammar already loaded too), `loadGrammarsFor` and `newParser` on that host rejects or throws with the same code, and `loadedParserFor` returns `undefined`, also for a parser the host held before the abort. A call that was waiting for its grammar or its parser when the abort came rejects with the same code. Freeing a tree or a parser, and resetting a parser after a stopped parse, take a little of the runtime's memory too and can abort as a parse does: such an abort counts as one in the parse, so the call rejects with `ERUNTIMEABORTED` (`withParsedFile` in place of its function's result) and every later call is refused as above. After an abort the host frees nothing: `withParsedFile` does not delete its tree, also when another call aborted while its function ran, in which case the function's result stands, and the host does not delete the parser it made to retry a scanner trap. What stays unfreed is lost only with a runtime that is never used again. A new host over the same runtime does not help, so a consumer that meets this code restarts the process, or runs its parses in a process of their own. In 1.1 the host parsed the text a second time, as it does after a scanner trap, and rejected with the runtime's plain error.

What a consumer can rely on for time and memory: Runes bounds neither, and the callback bounds only time. A file that is not source code in its language parses in time that grows with its size and varies several-fold from one text to the next. Over seven random texts per size (printable ASCII with 5% newlines) in each of JavaScript, C#, Java, Python and Rust, with web-tree-sitter 0.27.2 and the 1.2.0 grammar pins on one machine, 250 000 characters took from 0.03 s to 32 s, and 1 000 000 characters from 0.06 s to more than 120 s, where a 120 s budget in the callback stopped one JavaScript text. These are samples, not bounds. On such text the calls came at most 76 ms apart in these runs, so a time budget there bounds the time to within that. Memory is another matter. A short text repeated over and over parses in memory that grows about fourfold each time the file doubles, and the runtime spends it in one step at the end of the text, with no call to the callback during it. On `a<a,` repeated to 16 KiB in a `.ts` file, the last call before the end saw the process at 101 MiB and the next, 281 ms later, at 461 MiB. On `int x = f(a < b, …` repeated to 16 KiB in a `.cs` file it went from 129 MiB to 1085 MiB in 802 ms. At 32 KiB the TypeScript shape reached 1.5 GiB and the C# one made the runtime abort at its 2 GiB limit, which rejects with `ERUNTIMEABORTED`. A callback that watches memory or time fires only once that memory is spent. A stop by position before the end of the text prevents it, and so does a time budget shorter than reading the text, but either refuses the file just as a size cap would. So the memory of a parse is bounded only by the size of the files a consumer parses (at 8 KiB the peaks measured over seven fresh processes each were 181 to 190 MiB for the TypeScript shape and 198 to 245 MiB for the C# one; at 16 KiB the C# one reached 1.1 GiB), or by parsing in a process with a memory limit of its own. A consumer that reads arbitrary files caps the size of the files it parses, skips binaries, passes a `progressCallback` with a time budget, and restarts the process on `ERUNTIMEABORTED`. The README's host section gives the measured numbers by language.

## `@chrisdudek/runes/mcp`

The MCP server generated from a table, the spawn executor, the stdio transport, and the pieces a consumer with its own message handler reuses (`buildTools`, `argvFor`, `answersJson`, `commandForTool`, `toolName`, `InvalidParams`).

Two public commands may not give one tool name: `toolName` joins a command's words with `_`, a space and a dash alike, so `a a` and `a-a` would both be `<prefix>a_a`, and a call to that name could not tell which command it meant. `defineTable` refuses such a table and `buildTools` throws for one that skipped `defineTable`, each naming both commands; a command marked `internal` has no tool and takes no part in the check. The help tool (`ToolOptions.help`) is checked the same way, but only by `buildTools`, which alone knows whether it is on: with `help` given, a public command named `help` makes `buildTools` throw, naming the help tool and the command, because the server would answer that name with the usage text and the command would be unreachable; `defineTable` accepts such a table.

The in-process executor is internal: `inProcess`, `InProcessExecutor`, `CallContext` and the `Executor` union are not exported, and an in-process value given as `ServerOptions.executor` is outside the promise. No tool runs one: Jarl dispatches in process through its own message handler and `serveStdio`, and builds its refusals itself, so it never goes through the adapter's error document. The in-process `run` answers with the CLI's internal `CommandResult` and throws its internal `CliError` to give a refusal its `why` and `next`; exporting the executor without those would let a consumer signal only a `code`. A 1.x minor exports the four with `CommandResult` and `CliError` when a tool adopts the executor.
