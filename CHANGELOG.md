# Changelog

All notable changes to Runes are recorded here, one line per change. Runes follows [Semantic Versioning](https://semver.org/); one version covers every subpath.

## [1.1.0] - 2026-11-15

A minor release of the relation readers, for someone upgrading from 1.0.0. They find dependencies they used to miss in C#, TypeScript and JavaScript, Rust, Python, Java and Kotlin, and drop edges they reported by mistake. The API gains a file view, the C# project reference graph, diagnostics for configuration files that cannot be read, and `TargetResolver.classifyUse`. A call written for 1.0.0 works unchanged, and the new API is optional; the edges a call gets change as listed below, and the C# extract records changed shape (Before you upgrade).

### Before you upgrade

- **New edges.** The readers see dependencies 1.0.0 did not, so a graph that passed may show new refusals. Almost all of them are dependencies your code has: declare them, or change the code. The forms: in C#, type arguments of generic calls, `global::` forms, attributes, tuples, delegates, type tests, `using static`, unused using aliases and the implicit `Program`; in TypeScript and JavaScript, solution-style tsconfig paths, workspace and `file:` bindings, package entries under build output, and configs saved with a byte order mark; in Rust, brace-list imports, every Cargo.toml spelling, target paths, `[patch]`, a dependency's re-exported extern crate, glob re-exports, proc-macro derives and names in scope; in Java and Kotlin, a type of the file's own package named without an import, so a test depends on the component that holds the class it tests; in Kotlin, annotated declarations and the types nested under a constructor on the line below its class header (ktfmt style); in Python, namespace packages and distributions that share one (poetry gains 53 edges, Airflow 604); in PHP and C, a `composer.json` or `compile_commands.json` saved with a byte order mark.
- **Edges that go away.** Some edges of 1.0.0 named a file the language does not reach: a C# type or extension method of a project the caller cannot see, an extension call an instance method takes, a Rust file no `mod` declares or that is no crate root, a TypeScript export target of the wrong condition or an extensionless pattern target, a workspace package that pnpm or a version range does not link, and an import between modules of a Python folder put on `sys.path` only by configuration (an Airflow dags folder). A relation you declared only for such an edge has no code behind it after the upgrade.
- **Rust without an edition.** A Cargo.toml that names no `edition`, and inherits none from its workspace, is read as edition 2015, as Cargo reads it, so a `use` of a dependency there needs `extern crate` to give an edge. Such a repository can show fewer cross-crate relations than on 1.0.0; adding `edition = "2018"` or later to the manifest brings them back. On the Rust repositories of the corpus no manifest omits the key.
- **The modelled TypeScript version.** A package's `types@<range>` export keys are read as TypeScript 7.0.2 reads them, whatever TypeScript your project uses: `types@>=7` and `types@7.0.2` are entered and `types@<7` is passed over. A project on an older TypeScript whose dependency writes such keys can get its edge to another declaration file than its own compiler picks. A tsconfig that leaves `module` or `moduleResolution` unset is read with the defaults of TypeScript 6 and later (`module` from `target`, Bundler unless `module` says otherwise).
- **Stored results.** The extractors of C#, Rust, TypeScript, Java and Kotlin changed their output and their `rev`, so hints and extracts stored by 1.0.0 are stale. A stored C# extract keeps its new fields `fileLocalTypes`, `lists` and `receiverTypes` beside `refs`: without `lists` and `receiverTypes` the calls and receivers that name them give no edge, and without `fileLocalTypes` a `file` type of the file is read as published.
- **The C# extract's shape.** The per-language extract records follow their extractor's `rev` and may change shape in a minor release (`docs/api.md`). In 1.1.0 the C# descriptor kind `'static'` is now `'target'`, and `fileLocalTypes`, the scope's `prefixDecls`, `aliasDecls`, `staticDecls` and `globalStatics`, the descriptors' `at` and `CsharpProjectScope.statics` are new required fields. Code that reads what `extractCsharpRefs` returns needs no change; code that matches the kind `'static'` or builds these objects itself does.
- **Symbol tables.** The C# and Rust extractors declare new per-file keys (`base:`, `members:`, `methods:`, `shapes:`, `mod:`, `modfile:`, `glob:` and the others `docs/api.md` names). A consumer that builds its table from every file's declarations needs no change. One that compacts or filters its table keeps these keys whole, or loses the edges that go through them.

### Added to the API

- `FileView` and `listedFileView`: `makeResolvePathToFile` and `buildCsharpProjectScopes` take an optional view over the paths and contents of one commit, so an untracked or ignored file on disk (a built `dist/`, a generated `.svelte-kit/tsconfig.json`, an installed package, a `.csproj` the commit does not hold) cannot decide where an import lands. Without a view the disk is read as in 1.0.0.
- `ResolvePathOptions.onDiagnostic` and `RelationDiagnostic`: a `tsconfig.json`, `jsconfig.json`, `package.json`, `composer.json` or `compile_commands.json` that does not parse, or a `pnpm-workspace.yaml` whose `packages` list cannot be read, is reported once per file with the code `config-unreadable`, with its line and column where the parser or the offending token tells them, never a guessed one; a package entry no tsconfig maps back to source is reported as `package-entry-missing`. Resolution itself is unchanged.
- `buildCsharpReachability` and `Reachability`: the reference graph of a repository's C# projects, which `makeResolver` reads to bind a name only in a project the caller can reach.
- `TargetResolver.classifyUse(candidates, fromFile, language)`, which `makeResolver` provides, answers one use as the edge walk reads it. Its `ambiguous` answer names the candidate files (a Java or Kotlin star import, a C# partial type, a name several owners declare, a Go package whose files two owners hold). Its `absent` answer says, in TypeScript, JavaScript, Python, Go, Rust, PHP, Java, Kotlin and C#, whether the use leaves the repository (`outside`: an installed package, the standard library), names a place of the repository that binds no file (`unfollowed`), or binds a file no owner maps (`unowned`). `ResolverDeps.resolvePathToFile` may carry `explainMiss` for this, and the function `makeResolvePathToFile` returns has it. A later 1.x release may add values of `reason` and of `explainMiss`'s answer, so read a value you do not know as no reason; the three kinds of answer stay. `classify` and every edge answer as before.
- For a consumer that runs its own pass: the optional fields `samePackage` (a Java or Kotlin reference sees only the definers its source set can see), `onDemand` (the star imports a Java or Kotlin simple name may come from, which only `classifyUse` reads), `shadow`, `within`, `attribute`, `takes` and `unless` on `TargetHint`, and `callForm` (`'require'`, `'import'` or `'esm'`) on its path form; `SymbolSetMember.shadow`; the methods `SymbolTable.hasNamespace` and `SymbolTable.valuesOf`; `ResolverDeps.reach`, a `Reachability`; and two optional arguments of `ResolverDeps.resolvePathToFile`, the `SymbolTable` (fifth) and the call form (sixth), which `makeResolver` passes. The C# extract gains `fileLocalTypes` and, on its `scope`, `prefixDecls`, `aliasDecls`, `staticDecls` and `globalStatics`, with the optional `lists`, `receiverTypes` and descriptor `types`; `CsharpProjectScope` gains `statics`, `CsharpGlobalFacts` the optional `globalStatics`, and `CsharpUsesOptions` the optional `projectGlobalStatics`. `docs/api.md` describes each, and also how the C# extract keeps a using written after `global::` and that the `target` descriptor has no `nearest` field.

### C#

- Types named only as type arguments of a generic method call (`services.AddScoped<IFoo, Foo>()`, `sp.GetRequiredService<T>()`, `Substitute.For<T>()`, `Array.Empty<T>()`), and types in `new T[n]`, `stackalloc T[n]`, `foreach (T x in …)`, `out T x` and a typed deconstruction, count as dependencies.
- A tuple type with named elements inside a generic argument, one or two levels deep (`new List<(Order Item, int Index)>(n)`, `Make<List<(Invoice Doc, int I)>>(n)`), gives edges for its element types and the enclosing generic types, and so does an unnamed element beside a named one, written qualified, with `global::` or as a generic (`new List<(Order O, Shop.Core.Customer)>(n)`); the element names never do.
- `global::` reaches only the global namespace: `global::Settings`, `global::Box<T>`, `WebApplicationFactory<global::Program>`, attributes (`[global::A.Bar]`, `[global::Foo]`, `[global::Gen<Order>]`) and static members (`global::Clock.Now()`, as generated gRPC and protobuf code writes them) bind the type of the global namespace, ahead of a same-named type in an enclosing namespace.
- An attribute behind a qualifier (`[A.Gen<Order>]`) or a using alias (`[S::Foo]`, `[S::Gen<T>]`, `[S::Core.Mark]`) gives its edge. `[Foo]` binds the reading that is an attribute class: a plain class `Foo` beside `FooAttribute` does not take the edge, a nearer `FooAttribute` wins over a `Foo` from a using, and a domain class named like a framework attribute (`Route` beside `[Route]`) gives no edge.
- A reference to `Program` (`WebApplicationFactory<Program>` in an integration-test project, `ILogger<Program>`) binds the `Program` of the file's own project first, then of a project it references, whether the class is declared in source or generated by the compiler for a file of top-level statements. A class file no longer gets an edge to another project's `public partial class Program { }`, and when a project references two projects that each have a `Program` the reference stays unreported.
- A name equal to a type parameter in scope (`T x;` inside `T Resolve<T>()`, `Entity` inside `class Repository<Entity>`) refers to that type parameter, never to a same-named type of the repository; the scope is the declaration's own, so `Entity.Create()` in a sibling class gives its edge.
- A comparison pair whose left operand is a member access (`Within(x.Low < Order, j > Max)`) is read as two comparisons, not as a generic type, and `F(x < Limits.Max, y > z)` gives the edge to the type `Limits`.
- A delegate declaration is a type (`delegate void Handler(int id);`, nested and generic ones too), and these forms give their edges: `o is App.Models.Order`, `Models.Order =>`, `o is Note[]`, `o is Box<Item>`, every type of a chain of `is` tests such as `item is A || item is B`, dotted ones included (`x is App.Models.Order || x is App.Models.Line`; the first type of such chains alone gives jellyfin 63 more references), a `ref Order` return or local, `from Row r in xs`, `join Cell c in ys` and `delegate*<Order, void>`.
- A dotted constant in a pattern whose first name the file also declares as a property, a local or a parameter (`x is Status.Active` beside `public Status Status { get; set; }`, a switch arm `Status.Done =>` beside `var Status = ...`) gives its edge to the type, as C# reads such a name.
- The member path of an extended property pattern (`x is { Order.Id: 3 }`, `{ Order.Customer.Name: "a" } =>` in a switch) names members of the value tested and gives no edge to a type named like one of them, as `x is { Order: { Id: 3 } }` gives none; a constant or a type pattern after the colon (`{ Order.Kind: Kind.A }`, `{ Order: Orders.Order }`) still gives its edge.
- A name with type arguments binds only a type with that many type parameters, and a bare name only a non-generic type: `Result<int>` does not bind a nearer non-generic `Result`, and `Result` and `Result<T>` in two components each keep their edge. C# declaration keys of generic types carry their arity (``Result`1``).
- A call `x.Name()`, a read `X.Member` or a type binds a declaration of the repository only in a project the calling project can reach: through a `ProjectReference`, or a `<Reference>` (by name, by the file name of its `Include`, or by `HintPath`, as an element or an attribute) or `<PackageReference>` to an assembly or package the repository builds, with `<AssemblyName>` read from `Directory.Build.props` and its imports. A framework method that shares its name with an extension in an unreferenced project no longer gives an edge. A project that uses a reference or an unconditional import Runes cannot resolve reads as able to reach every project, so nothing real is lost.
- A reference marked `ReferenceOutputAssembly="false"` gives the referencing project no sight of the referenced project, and one marked `PrivateAssets="all"` is not passed on to its consumers. A file a project takes out with `<Compile Remove>` declares nothing there, and a `<Compile Include>` that links a file from outside the project adds that file and nothing else; that file is also a caller of the linking project's references.
- An `internal` type or extension class of another project counts only where that project names the caller with `InternalsVisibleTo`, and a `partial` part without an access modifier is internal where another part of the same project says so. A `Condition` that holds a raw `>` before an item's `Include` or `Project` (`Condition="'$(LangVersion)' > '10'"`) is read whole, so the `Reference`, `PackageReference`, `Using`, `AssemblyName`, `Import` or SDK after it counts.
- A using alias to a type (`using F = A.B.Foo;`, `using H = global::A.B.Foo;`, `using R = A.B.Repo<A.B.Foo>;`, the generic type and each type argument) gives its edge whether or not a line uses it, as `using static` does; `nameof(Foo)` stays silent by design.
- A using alias is read where its directive stands, the same on the directive line and on every use: in the namespace body that holds it, with the usings and aliases of the blocks around it. On the directive line of an unused alias, a first name that a nearer namespace or type declares hides a farther one: `namespace App; using M = Models;` gives no edge to a global `Models` beside a namespace `App.Models`, and `using O = Shop.Ordering.Order;` gives its edge where nothing nearer is named `Shop`.
- A plain `using N;` inside a namespace block reaches only the references of that block and the blocks nested in it, at that namespace, before the next namespace outward and the project's global usings. The namespace it names is read where it stands (`using Core;` inside `namespace A` names `A.Core` when the repository declares it), unless that nearer namespace lives only in a project out of the caller's reach.
- A type or a static class of the global namespace binds before what the compilation unit's usings import, for type names and extension calls alike: `using Lib;` beside a global `Order` gives the edge to the global `Order`. Where several projects declare such a global extension method and the reference graph cannot rule them out, the call has no edge (two calls in eShop).
- A simple name inside a type reads the nested types of each enclosing type, from every part of a partial type, and then those of its base classes in the repository, before any namespace, alias or using: `Command` inside `CreateOrder.Handler` names `CreateOrder.Command`, `Options` in `class MyHandler : HandlerBase` names `HandlerBase.Options`, and `Worker.Options.Parse()` in a file that declares `Worker` gives its edge.
- A name that a class has as a member, inherited from a base class of the repository or declared in another part of a partial class, is read as that member: `Settings.Get()` there gives no edge to a static class `Settings`, and an extension call on such a member binds its extension method. An explicit interface implementation (`ISettings IHasSettings.Settings => …`) does not hide the class `Settings`.
- A dotted name binds its first name at the nearest place that knows it: in `namespace App.Web`, `Data.Row.Parse()` and `o is Data.Row` name `App.Data.Row`, not a class `Data` of the global namespace.
- An extension method takes a call only where C# would choose it. The receiver's written type, its base classes in the repository and the other parts of a partial type have no instance method of that name that takes the call's argument counts (`order.Validate()`, `this._config.Get(key)`); the extension method takes the call's number of arguments (`sessions.FirstOrDefault(s => s.Active)` gives no edge to a `FirstOrDefault<T>(this IReadOnlyList<T>)` that takes none); and an instance method of the same counts that cannot take an argument by its written type leaves the call to the extension (`manager.GetItemById(id)` with `string id` beside `GetItemById(Guid)`). Where both take the same counts and the argument types are not written, the instance method is taken.
- Among extension methods of one name in several imported namespaces, a call whose receiver type is written picks the one whose first parameter takes that type; otherwise they stay ambiguous, also when one is in the caller's own project, since the compiler chooses by overload. A private extension method counts only in its own file, and an internal one only in its assembly and its friends.
- `using static T;` imports the nested types and the extension methods of `T` at the level of its directive (the compilation unit, a namespace body, or the whole project for `global using static`), and a generic `using static Repo<Order>;` gives the edges of `Repo` and `Order`. Two `using static` classes that each declare an extension method of one name give no edge.
- A `file` type, and a type nested in one, binds by its name inside its own file, also as a using alias or `using static` target and after an alias qualifier, so a public type of the same name in another file gets no edge from that file. A `file` type reads the nested types, members and instance methods of its base classes, and a `file` interface the nested types of its base interfaces.
- A large C# repository is read in less time than with 1.0.0: reading the declarations and references of its files takes 0.65 to 0.70 of 1.0.0's time on jellyfin and about 0.75 on eShop, and resolving its references about a fifth (jellyfin: 5.1 s against 24.2 s on one machine). A file of many deconstruction lines, named-tuple generics or broken lines with dotted names is read in time proportional to its size.
### TypeScript and JavaScript

- Path aliases in a solution-style tsconfig.json (`files: []` plus `references`, as Vite and create-vue scaffold it) come from the referenced config whose `include` holds the file, matched as tsc matches it (a wildcard skips dot-names and node_modules, an include ending in `**` matches nothing, `outDir` and `declarationDir` are excluded when no `exclude` is set), and from the first direct reference that holds it before any nested one (Airflow UI's `tests/e2e/fixtures`). When several referenced configs hold the file and disagree, the import stays unresolved. A `.vue` or `.svelte` component reads jsconfig.json paths as a JavaScript file does.
- A bare import binds to the package the importing package.json declares under that name with a `file:`, `link:`, `portal:` or `workspace:` spec; otherwise, in a repository that declares a workspace (package.json `workspaces` or pnpm-workspace.yaml, brace globs included), to a workspace member. A test fixture or mock named like a dependency or a member no longer takes the import.
- A workspace package declared by a version range or a tag binds only where the package manager links it (the root's `packageManager` or its lockfile): npm and yarn for a range the package's version satisfies, pnpm only with `link-workspace-packages` on. In a pnpm workspace a bare import of a member binds only where the importing package, or a project above the file up to the workspace root, declares it, unless the workspace hoists publicly (`shamefully-hoist`, `node-linker=hoisted`, a `public-hoist-pattern`); a package's import of its own name binds there only when it declares `exports`.
- Layouts that npm, pnpm and Node resolve resolve here too: a workspace member with a workspace of its own sees the enclosing workspace's members, a package with `exports` imports itself by name, a file under a package.json that only sets `"type"` sees the `file:` and `link:` dependencies of the package around it, and a referenced tsconfig that extends a generated base missing from the commit (SvelteKit, Nuxt) affects only the files it may hold.
- A workspace package whose `exports`, `types`, `typings`, `module` or `main` names build output the repository does not hold (`./dist/index.js`, `./build/index.d.ts`) binds the source it is compiled from, read through the package's own `tsconfig.json` or `tsconfig.*.json` (`outDir` back to `rootDir`, also when written with a trailing slash, `"./dist/types/"`). A dual package that tsup or unbuild builds into `dist/index.mjs`, `.cjs`, `.d.mts` or `.d.cts` from `src/index.ts` maps back the same way; a `.mts` or `.cts` source of the same name is read first.
- An import binds the target of a package's `exports` or `imports` that TypeScript chooses for the importing file: `import` or `require` by the file's module format, `types`, `node` except under Bundler, and the tsconfig's `customConditions`, with a solution tsconfig's references searched as tsserver searches them (`next-intl/plugin` under Bundler takes its `import` branch). In a file no tsconfig covers it reads the conditions Node and TypeScript use, so a `react-server`, `workerd`, `edge-light` or `react-native` build is not taken for `default`.
- A `require('x')` call and `import x = require('x')` read the `require` condition; a dynamic `import('x')` reads `import`, except where the compiler emits it as a `require` (a `.cts` file, any file under `module` commonjs); an import type (`typeof import('x')`, `import('x').T`) reads its file's format; and the `resolution-mode` import attribute (`import type { T } from 'x' with { 'resolution-mode': 'import' }`, also when the clause starts on the next line) reads the condition it names. `export interface I extends import('x').T {}` gives no edge.
- Under a tsconfig that extends a preset the file view does not hold (`@tsconfig/node20`, installed under node_modules), exports are read as the compiler reads them wherever the config, the file kind or the call form decides; where the preset alone decides, the import binds the first listed target that a possible reading names.
- An `exports` or `imports` pattern target written without an extension (`"./src/*": "./src/*"`, `"#u/*": "./src/u/*"`) names that path and no `.js` or `.ts` file beside it, as Node and TypeScript read it, so such an import gives no edge to a file it does not name (react loses 40 edges of this kind); a target that writes its extension (`"./src/u/*.js"`) binds its file.
- A tsconfig `extends` naming a package (`"extends": "@acme/tsconfig"`) follows the same workspace rule as a bare import and reads the package as tsc does: its `exports` (conditions, patterns), then the `tsconfig` field of its package.json and its `tsconfig.json`. `@acme/tsconfig/base` also tries `base/tsconfig.json`, and a subpath that is a directory with its own package.json reads that package.json's `tsconfig` field.
- Files the consumer excludes (git-ignored build output under dist/, a generated `.svelte-kit/tsconfig.json`) are neither import targets nor configs to read; git-ignored paths still have to be passed as excluded, or left out of the file view.
- A tsconfig.json, jsconfig.json or package.json saved with a UTF-8 byte order mark (as Visual Studio writes it) is read like any other, and so is a CR-only `tsconfig.json` with a `//` comment or `pnpm-workspace.yaml`.

### Rust and Cargo

- A brace-list import with no path prefix (`use {core_lib::Invoice, std::fmt::Debug};`, nested, or `pub use {…}`) gives an edge for every item.
- Cargo.toml dependencies are read in every TOML spelling: dotted keys (`foo.workspace = true`, `foo.path = "../foo"`, `dependencies.foo.path`, `workspace.dependencies.foo.path`, also under `[workspace]` and `[target.<cfg>]`), one inline table for the whole section (`dependencies = { util = { path = "../util" } }`), inline tables holding multi-line arrays, and strings in any TOML form (multi-line, with escapes). The first declaration of a crate wins over a later `[dependencies.<name>]` table.
- `package = { name = … }` and `lib = { name = …, path = … }`, inline or dotted, give the crate name and library path as the `[package]` and `[lib]` tables do. A `[lib]` path in a subdirectory of `src/` resolves `crate::` paths against that subdirectory, and with a `[lib]` path outside `src/` the modules of `src/main.rs` bind `crate::` within the binary.
- `[[bin]]`, `[[test]]`, `[[example]]` and `[[bench]]` paths, also written inline (`bin = [{ path = … }]`), root their crates, so `crate::`, `self::` and `super::` paths and `mod` lines in those files resolve inside them (ripgrep's crates/core/main.rs, zed's tests/integration). `[package] build = "<file>"` roots the build script at that file, and with `build = false` a `build.rs` at the package root is no build script.
- Crate roots follow Cargo's target discovery: `autobins`, `autolib`, `autotests`, `autoexamples` and `autobenches = false`, `bin = []`, an inferred target dropped where a declared target of its kind has its name or path, a `[[bin]]` without a `path` at its legacy place, and a library found at `src/<name>.rs`. In edition 2015 a declared `[[bin]]`, `[[test]]`, `[[example]]` or `[[bench]]` turns auto-discovery of its kind off, a helper such as `tests/common/mod.rs` binds the one declared root beside it, and a `[[bench]]` named `bench` falls back to `src/bench.rs`. Under `autolib = false` without a `[lib]` table, a `use` of the package's own name gets no edge into `src/lib.rs`.
- The edition decides how a `use` path reads, as in rustc: `edition = { workspace = true }` takes the workspace's edition, and an edition written on `[lib]` or a target table decides for that target's files. In edition 2015 `use a::b` and `use ::a::b` are relative to the crate root (`use Error;` for an item the root binds at its top level), a root's own `mod util;` wins over a path dependency `util` unless the root writes `extern crate util;`, and `use app::Engine;` in a target of the package `app` reaches its library only through `extern crate app;`. From edition 2018 a path that starts with `::` names a crate only.
- From edition 2018 a `use` path that starts with a name in scope is followed: a module the same module declares (`mod shapes; pub use shapes::Circle;`) or a name another `use` there brought in (`use crate::shapes; use shapes::round::Arc;`), before a crate of the same name.
- A path through an extern crate name gives its edge: a dependency's re-exported extern crate (`grep::printer::Standard`, where `grep` declares `pub extern crate grep_printer as printer;`), and `extern crate engine_core as core2;`, which makes `core2` name the in-repo dependency in its module, in function bodies and blocks too, through `self::` and `super::`, and when written in a branch of `cfg_if!`. A `mod` of that name in a function body hides it.
- In a package with several crate roots over `src/` (`src/lib.rs` beside `src/main.rs`, a `[[bin]]` in `src/`), `crate::Item` in a module binds the root that a chain of plain `mod` declarations leads to, read from parse trees, and a module of a binary reads bare `use` paths in that binary's edition. A `mod` under a `cfg` counts after a plain one. A `mod` with a `path` attribute, a `cfg_attr` or an attribute macro on it, one written by a macro and one pulled in by `include!` are not followed; where no chain reaches a file, the roots are tried in the order of 1.0.0, the library first. A module two roots declare gives no edge to a root item.
- A directory of `src/bin/` without a `main.rs` is a module of the binary that declares it, the one that declares it without a `cfg` where another does so only under one, so `crate::`, `super::` and edition 2015 bare paths in its files bind that binary's tree. When no binary or several declare it, those paths give no edge.
- A file is a module only where a `mod` declares it: `use crate::util::parse;` binds the file that defines the function `parse`, not a leftover `util/parse.rs`, and `crate::serve()` in one binary never binds another binary's root file. A `mod x;` in a branch of `cfg_if!` gives its edge, and a `#[path]` attribute separated from its `mod` by a comment or another attribute is seen.
- A file loaded through `#[path = "…"]` owns its directory as a `mod.rs` does, so its own `mod x;` binds the file beside it, and `super::` in it names the module of the file that loads it. A `#[path]` inside an inline module, also in a `lib.rs` or `main.rs` that is no crate root, loads relative to that inline module's directory.
- A `crate::` path, or a path into an in-repo path dependency, binds the crate-root file only for a name its top level binds, read from the parse tree: an item it defines, one of `lazy_static!`, `thread_local!`, `bitflags!` or `cfg_if!`, a derive of `#[proc_macro_derive(Builder)]` (also through `cfg_attr`), a name a top-level `use` brings in, and a name a glob re-export brings in (`mod types; pub use types::*;`, also two globs under opposite `cfg`s). A name in a string, a nested function or another macro's body binds nothing.
- A derive macro of an in-repo proc-macro crate gives its edge: `use derive_kit::Builder;` binds the crate whose root has `#[proc_macro_derive(Builder)]`, and so does a facade's `pub use kit_derive::Builder;`. The helper attributes in `attributes(…)` are no names to import.
- A `[patch.crates-io]`, `[patch.<registry>]` or `[patch."<git url>"]` entry with a `path`, in the workspace root manifest or the manifest of a package that is its own workspace, replaces the dependency of that name for every package of the workspace, `package =` renames included, so `use kit::Engine;` binds the patched library. A `[patch]` in a member manifest is ignored, as Cargo ignores it.

### Python

- In a PEP 420 namespace package (google-cloud-* libraries, poetry's src/poetry), `import logging`, `import json` or an external library import from a sub-package binds to the library, not to a same-named sibling such as google/cloud/logging/. Besides the project roots, imports are searched from the importing file's own directory, a directory holding conftest.py and no `__init__.py` (pytest), and one holding manage.py (Django); a standard-library name binds only in the file's own directory or at the repository root. A folder put on `sys.path` only by configuration (an Airflow dags folder, a `PYTHONPATH` entry) is not searched, so imports between its modules give no edge.
- When several distributions share a pkgutil-style namespace package (Airflow's core, task SDK and providers each ship `airflow/__init__.py`), `from airflow import settings` and `import airflow.settings` report the dependency on the distribution that holds the module.
- In a uv or Poetry monorepo with many pyproject.toml projects, one resolver per pass remembers its probes and looks only at the projects that hold the imported package, with the same relations reported.

### Java and Kotlin

- A Java or Kotlin file that names a type of its own package by its simple name, without an import (`Owner o = new Owner();`, `val o: Owner = Owner()`, `Owner.make()`, `Owner::class`, `@Mark`), gives an edge to the owner of that type, within the source set: code under `src/main` never sees a class that only `src/test` declares, and a test sees `main`, its own set, the `testFixtures` of any module and every test set of another module. A class of either language counts, and a Java annotation type is declared. Nothing is read where the name means something else: a type parameter in scope, a declaration of the file, an import or alias of that name, a variable that obscures it, the root or unnamed package, and in Kotlin a file whose declarations could not all be read.
- In Kotlin the precedence is the language's: an explicit import or alias wins, the package beats a star import and the default imports, and a capitalised top-level function or property used as a receiver or callee binds too; a lowercase name (`helper()`, `val limit`, `"x".shout()`) is never read.
- In Java, a simple name of `java.lang` written without an import (`String`, `Override`), and in Kotlin a name of its default imports (`String`, `List`, `Throws`), is read as the standard library's after the file's own package, so `classifyUse` answers that it leaves the repository. A simple name a star import of the repository declares stays the repository's whatever the default imports hold, and one a library's star import can give (`List` under `import java.util.*;`) leaves it; no edge changes. In Java, `TypeAdapters.FactorySupplier` written in the package of `TypeAdapters` binds the file that declares the member type.
- Kotlin imports give an edge for annotated top-level declarations (a meta-annotated annotation class such as a Dagger or Hilt qualifier, an annotated enum with one entry, an annotated data object, `expect class` or `const val`) and for the types nested in a class whose primary constructor sits on the line below its header (ktfmt style), with or without `val`/`var` parameters. Where a header cannot be joined to its constructor, the enclosing type is marked as not fully read, and a damaged declaration is read the same wherever it stands in the file.

### All languages

- A `composer.json` or `compile_commands.json` that starts with a byte order mark is read, so PHP imports through its autoload maps and C includes through its include roots resolve.
- Reading takes time in proportion to the size of the file: walking a syntax tree, also a long flat run of error nodes (a binary file named .ts) or a tree nested hundreds of levels deep, which walks without running out of stack; extracting a TypeScript file of malformed lines such as `g<import('x').T>(`, a Kotlin file with many damaged declarations, and a Java, Kotlin, PHP, Rust or Ruby file of tens of thousands of unterminated strings. The edges are the same.

### Command table

- `defineTable` refuses a table in which two public commands give one MCP tool name (`a a` and `a-a` both `<prefix>a_a`), and `buildTools` refuses that and a public command named `help` while the help tool is on, naming both, where the tool used to run whichever came first.

### Known limits

- C#: a member inherited from a base class outside the repository (ASP.NET Core's `ControllerBase.User`) keeps the reading of 1.0.0, so a type of the repository with that name still gets the edge.
- Rust `[patch]`: the version of the patched crate is not compared with the dependency's requirement, a `[workspace]`'s `exclude` list and `package.workspace` are not read (the nearest manifest with a `[workspace]` table above the package is its root), and a GitHub URL is matched as written, where Cargo lowercases it.
- Rust: a library rooted at the package root (`[lib] path = "lib.rs"`) whose `lib.rs` holds only an inline module with a `#[path]` module gives no edge for the `mod` lines of the loaded file.
- `classifyUse` answers `outside` for a type an annotation processor generates into the file's own package (`AutoValue_Use`, `DaggerAppComponent`) where a star import of a library could give its simple name, since the repository holds no file for it; without such a star import it answers `unfollowed`.
- `classifyUse` in Python and PHP answers `absent` with the reason `unfollowed`, and names no candidates, where several roots or projects could hold the use.
- C#: a chain of `is not` tests of dotted types (`x is not App.Models.Order || x is not App.Models.Line`) gives no edge.

New property tests with a printed, replayable seed (`RUNES_PROPERTY_SEED`): the tool-call-to-argv round trip through `parseArgs` over random tables and values, flag order on a command line, `UsageError` as the only refusal, mutual exclusion of the lock across processes and async holders, `withLock` against a model of the staleness rules, and the vendor gate against random edits. New tests for the source build and the download of grammars (a stand-in tree-sitter-cli and a stubbed fetch), the language table, `destroyParseCache`, and `writeAtomic`'s mode.

Each call keeps its own time limit, counted from when it starts running, and its own cancel; answers go out as calls finish. The default stays one call at a time, in order, and `createServer` refuses more than one with an in-process executor, whose run cannot be stopped. `McpServer` gains `concurrency`, which `serveStdio` reads; a server object without it runs one call at a time as before.
